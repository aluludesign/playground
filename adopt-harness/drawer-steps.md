# 抽屜的「四個尺寸」以前不是尺寸

**Lulu 回報**:「desktop 尺寸右邊的地圖 drawer 沒有固定在四個尺寸會亂跑。」
追問之後確認她講的是**拖曳**:可以手動拉寬,放手會吸附到四檔中最近的一檔。

## 量到的

| 視窗寬 | 抽屜寬 |
| --- | --- |
| 1160 | 580 |
| 1172 | 586 |
| **1176** | **294** |
| 1280 | 320 |
| 1600 | 400 |

**視窗改 4 個像素,抽屜砍一半。** 而且更違反直覺的是整體趨勢:
**視窗越寬,抽屜反而越窄**(1100 給 550,1280 給 320)。

## 根因:那四檔是「視窗的 1/4、2/4、3/4、4/4」

所以「吸附到第 2 檔」**不代表一個寬度** —— 視窗一變,同一檔就是另一個寬度。
「固定在四個尺寸」這句話從來沒成立過,因為那四個東西不是尺寸,是比例。

### 懸崖不是四捨五入寫錯

預設檔位以前是 `Math.round(440 / quarter())`。在 1173px 附近:

```
第 1 檔 = 293    |440 - 293| = 147
第 2 檔 = 587    |440 - 587| = 147
```

**離 440 剛好一樣遠。** 兩檔之間根本沒有靠近 440 的東西,所以那裡必然有一個分界,
往哪邊倒都會跳。**用相對比例去反推一個絕對的預設值,一定會在某處斷掉。**

> 這個區分決定了修法:如果是寫錯,修四捨五入就好;**是結構問題,就得換掉那個結構。**

## 改了什麼

- **四檔改成固定像素**:`[360, 480, 620, 800]`,預設第 2 檔(480)。
- **吸附改成比像素距離**(`nearestStep`),不是「除以一檔有多寬」——
  檔位等寬時兩者一樣,不等寬時只有前者對。
- **resize 時重算的是「夾住」,不是「照比例縮放」**。

### 夾制的對象一開始挑錯了,而且是量出來才知道

第一版寫 `innerWidth * 0.82`。**桌機斷點是 641px,而那個夾制要 585px 以下才生效 ——
它從來碰不到。** 641px 的視窗於是吃到整整 480px 的抽屜,只剩 **161px** 給內容,
**比修之前的比例式(那裡剛好給一半)還糟**。

改成「至少留 320px 給版面」:

| 視窗寬 | 抽屜 | 剩給內容 |
| --- | --- | --- |
| 641 | 321 | 320 |
| 700 | 380 | 320 |
| 800 | 480 | 320 |
| 1100 | 480 | 620 |
| 1600 | 480 | 1120 |

**要保護的是底下的版面,不是抽屜** —— 抽屜一開 `body` 就 `padding-right` 同樣的寬度,
抽屜多寬,行程清單就少多寬。

## 驗收

- **`probes/drawer.js` 9 條,1100 和 641 兩個寬度都全過**(新寫的)。
  拿去跑 `main`:**6 條紅**
- 截圖**只有 07 變**(桌機抽屜),其餘十一張逐位元組相同;11 落在已登記的雙穩態
  (8px / 6 個單列群 / 1·1·2·2·1·1,簽章吻合)
- rebase 到合併後的 main 之後**重驗過**:`drawer` 9、`seek` 34、`geofix` 131 全過 ——
  **rebase 沒衝突不代表行為沒衝突**,那是兩件事

### 探針自己承認它在窄視窗下測不到東西

641px 下四檔全被夾成 321,所以 `want(2) === want(3)` ——
「吸到第 2 檔」和「吸到第 3 檔」量到同一個數字,**兩條都綠而且什麼都沒測到**。
探針現在會在輸出裡講出來:

```
吸附測得到嗎: **恆真,沒測到東西** —— 這個寬度下四檔被夾成同一個值 321px
```

> 不講的話,「641 也全過」會被讀成「窄視窗下吸附也驗過了」。
> 那是工具陷阱 12 的形狀,只是這次發生在我自己剛寫的斷言上。

## 第三輪:固定像素也不對 —— 最寬要是螢幕的 3/4

**Lulu 試完之後:「最寬是螢幕的 3/4,現在是 1/2。」**

`800px` 在她 1600 的螢幕上就是一半。**大螢幕買到的空間應該進得了抽屜,
而寫死的像素把它擋在外面。**

所以四檔改回比例,但**不是回到原本的 `k/4`**:

| | 舊的(`k/4`) | 現在 |
| --- | --- | --- |
| 範圍 | 1/4 … **4/4**(整個視窗) | 1/4 … **3/4** |
| 預設 | `Math.round(440 / quarter())` ← 懸崖的來源 | **寫死第 2 檔** |

`FRACS = [1/4, 5/12, 7/12, 3/4]`,1/4 到 3/4 之間四等分。
**懸崖那個修法保留**(預設不從目標寬度反推),被推翻的只有「檔位是固定像素」這一半。

量到的:

| 螢幕寬 | 最寬那一檔 | 佔螢幕 |
| --- | --- | --- |
| 1600 | 1200 | **0.750** |
| 1440 | 1080 | 0.750 |
| 1280 | 960 | 0.750 |
| 1100 | 825 | 0.750 |
| 900 | 660 | 0.733 ← 夾制生效 |
| 641 | 401 | 0.626 ← 同上 |

**夾制從「留 320px 給版面」放寬成 240px** —— 3/4 那一檔在 1100px 的視窗上只剩 275px 給版面,
而那一檔是**使用者自己選的**。夾制是防止版面被壓垮,不是替他決定要多寬。

> **兩輪都是「我挑了一個數字,而她的螢幕不是我假設的那台」。**
> 第一輪我挑 440 當目標寬度(懸崖),第二輪我挑 360/480/620/800(在 1600 上只有一半)。
> **能寫成比例的就不要寫成像素** —— 比例不需要知道使用者的螢幕多大。

## 第二輪:吸附根本沒生效,而我的探針說它過了

**Lulu 在 preview 上拖了一次:放開之後抽屜停在原地,沒有吸附。**

### 我的探針測了一條沒有人會走的路

第一版的 `drag()` 把 `pointerdown` / `pointermove` / `pointerup`
**三個事件全部丟在握把上、同一個座標**。真人拖的時候,游標第一下之後就離開
那條 14px 寬的握把了。

量出來的對照(這支探針自己跑的):

| 在哪裡放開 | 結果 |
| --- | --- |
| 握把上 | 700 → 吸到 640 ✓ |
| **body 上** | **500 → 500,完全沒有吸附** |

而 `grip.hasPointerCapture()` 回 **false** —— `setPointerCapture` 失敗了,
而它包在 `try/catch` 裡,**失敗是無聲的**。

> **判準(給下一個要測互動的人):** 合成事件對「點一下」夠用;
> 對**拖曳**不夠,因為拖曳的語意有一半在「指標抓取」和「事件落在誰身上」,
> 而那正是合成事件最不像真人的地方。
> **把落點當成變數測一次** —— 兩種落點結果不同,就代表**你的測法本身是那個結果的成因之一**。

修法:**移動和放開都綁在 `window` 上**,不是綁在握把上;
收尾用拖曳中自己算的 `liveW`,不從 `ev.clientX` 反推(`pointercancel` 的座標可能是 0,
那會吸到最寬那一檔);另外補 `blur`,因為指標離開瀏覽器視窗之後 `pointerup` 不一定回得來。

### 然後我又把一個好的修法判成壞的 —— 因為量錯東西

改完之後探針 6 條紅,而**程式是對的**。量出來:

| | `--drawer`(狀態) | `getBoundingClientRect()`(畫面) |
| --- | --- | --- |
| 放開當下 | **480px** | 520 |
| 350ms 後 | 480px | 480 |

`.sheet` 有 `transition: width .18s`,所以 rect 讀到的是**動畫跑到一半的值**。
而且它是**間歇的**:探針前面做得越多,`--virtual-time-budget` 剩得越少,
過場就越可能完全不推進 —— **斷言少的第一版過了,斷言多的這一版沒過,而程式一樣。**

> **量一個有過場動畫的東西時,先問你要的是狀態還是畫面。**
> 要狀態就讀來源(CSS 變數、dataset、localStorage);
> 要畫面就得等動畫結束,而那在虛擬時間下不保證會發生。

### 順手發現:這台機器上今天所有的量測,都是一個 9/19 的孤兒 server 服出來的

`probe.sh` 每次都會自己啟一個 server 在**寫死的 8998**。而機器上有兩個
**9/19 啟動、已經跑了 1 天 11 小時**的 Python server 還佔著 8998 / 8999 ——
新的綁不上,而**綁失敗是無聲的**。

共用工作樹裡它一直「碰巧」正確,因為那個孤兒的工作目錄正好是共用的 `.work/`,
而 `probe.sh` 每次重建同一個路徑。**從別的 worktree 跑就穿幫了**:
孤兒服的是共用那份,我的 `.work/` 在別的地方,於是 Chrome 抓到 404,探針什麼都沒回。

已經清掉。**登記兩件事給下一個碰 `probe.sh` 的人**:
1. server 啟動失敗要出聲(現在是無聲的)
2. **埠是寫死的,而 worktree 讓鎖各自獨立** —— 互斥會悄悄失效。
   這一輪的做法是手動去拿共用那把鎖,那是權宜之計不是解法。

### 順手撞到已登記的盲區,但這次的觸發源是躲不掉的

產出的 CSS 多了一個 `.blur{--tw-blur:blur(8px)}` —— 沒有任何 markup 用它。
來源是我新增的那一行:

```js
window.addEventListener("blur", stop);
```

**Tailwind 掃原始碼,把 JS 裡的 DOM 事件名當成了 utility class。**

ADOPTION 的「已登記的盲區」記過這件事(所以工程文件不放 `tokyo-trip/`),
但那幾次的觸發源是**文件裡的散文** —— 把文件搬走就解決了。
**這一次不行**:`"blur"` 是 DOM 事件的名字,不能改寫。

無害(多約 200 bytes、沒有人用),但它讓那一節的結論要修一句:
**「把工程文件搬出掃描範圍」不是完整的解法,因為程式碼本身就會命中。**
真正的解法是限制掃描範圍或加 ignore,而那是 design-system 那邊的事。登記,不在這一輪動。

而**合成事件的落點是探針自己決定的** —— 我的第一版探針把三個事件都丟在握把上,
9 條全綠,而真人拖一次就翻掉了。

> **這個修法沒有任何工具驗得到。** 探針能證明的最多是
> 「在握把上放開和在 body 上放開會得到同一個結果」——
> 那證明的是**我的測法不再是結果的成因**,不是「真人拖會吸附」。

**涵蓋到哪裡為止:** 她確認的是「吸附會發生」。
**沒有涵蓋**:拖到最寬／最窄時版面好不好讀、拖一半把游標移出瀏覽器視窗再放開
(那是 `blur` 那條收尾,合成事件測不到)。那兩條仍在下面。

> 這是這個專案第四次「真人抓到工具抓不到的東西」——
