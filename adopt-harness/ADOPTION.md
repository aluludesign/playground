### 第四塊留下一件要真人做的事

這一塊整個決定(保留 `:521` 的 16px)就是為了防 iOS Safari 對焦放大,
而**九張截圖和探針全部是 macOS 上的 headless Chrome,驗不到它**。
量到的只有「390px 下 29 個控制項改完仍然全部是 16px」——
那是**觸發條件不成立**的證據,不是**行為沒發生**的證據。

> **要一個真人拿 iPhone 打開網站、點進「加行程」的任何一個欄位,看版面會不會跳。**
> 那五個人就是在 iPhone 上記帳的。

第五塊新增的 10 / 11 兩張圖**一點忙都幫不上**:多了 14 個畫得出來的欄位,
一個都不能回答 iOS 的問題,因為它們一樣是 macOS 上的 headless Chrome。
**工具能做的事和該做的事之間那道界線,五塊下來一步都沒有移動。**

### 線上現在是什麼:這份文件不回答這個問題

**以前這裡寫著答案,而那個答案過期了兩次。**

第一次寫成「還沒推的:接線和第一塊」,寫下之後又推了一次,沒回頭更新。
第二次寫成「`origin/main` = `9262c9a`、mono 尚未推送」,而 mono 那時早就上線,
**那五個人已經看得到了**。兩次都是同一個結構問題:
**把一個每次 push 都會變的事實,寫進一份不會自己更新的文件。**

而且第二次過期的時候,這一段下面就已經寫著「不要從未推送清單反推、要自己跑這三行」——
**文件自己知道答案會過期,卻還是把答案留在上面。** 警告擋不住一個結構上就會壞的東西。

所以現在這裡不留答案,只留產生答案的方法:

```sh
git rev-parse origin/main
git merge-base --is-ancestor <commit> origin/main && echo 已上線
curl -s https://playground-beta-liart.vercel.app/ | grep -o "rm-chip"
```

**每一輪開工前自己跑一次。** 如果你正想在這份文件裡寫下它們的輸出 —— 不要,
那就是前兩次過期的寫法。

**推不推是 Lulu 的決定,不是接手的人的。**

### `SRC=`:不動共用工作樹也能截某個 commit 的樣子

「工具的陷阱 1」教的是「要截某個 commit 就先 `git stash` 或 checkout」——
**那等於動共用工作樹裡的 `tokyo-trip/index.html`**,而這個 repo 同時有別的
session 在動它,一塊一個人的時候還常常被明確要求不准碰。

```sh
git worktree add /tmp/wt 8b4ee7c
ln -s <repo>/design-system/node_modules /tmp/wt/design-system/node_modules   # 少了它會重編失敗
SRC=/tmp/wt/tokyo-trip ./shoot.sh pre-label-expform
SRC=/tmp/wt/tokyo-trip WIDTH=390 ./probe.sh probes/who.js
```

出處紀錄會多印一行 `來源`,而且**不是預設來源時會大聲說**下面那幾行 HEAD／工作樹
統計是主樹的、跟這批圖無關,另外印來源樹自己的 HEAD。

**`shoot.sh` 和 `probe.sh` 共用一把鎖,同一時間只有一隻跑得動。** 見「工具的陷阱 6」。

`probe.sh` 跟 `shoot.sh` 站在同一個地基上(同樣先重編、同樣灌 `fixture.py`),
所以**探針量到的數字和截圖是同一個世界**。沒有這一點,兩邊對不上帳。

用法:

```sh
cd <repo>/adopt-harness          # 注意:是 repo 根目錄,不是 tokyo-trip/ 底下
./shoot.sh <標籤>                 # 截一組,放進 shots/<標籤>/
python3 pngdiff.py shots/a/01-plan-mobile.png shots/b/01-plan-mobile.png
```

`shoot.sh` 會**自動先重編** design-system 的產出,不用手動跑 build。

**`probe.sh` 預設在 1100px 量,而九張截圖裡有七張是 390px。**
`index.html` 有一整段 `@media (max-width:640px)` 的覆寫,在 1100 量到的是那七張
**根本看不到的那一套值**。`block-04` 差點因此下相反的結論(見那一份的「新踩到的陷阱 3」)。

```sh
WIDTH=390 ./probe.sh probes/inputs.js     # 08 / 09 實際的寬度
./probe.sh probes/inputs.js               # 1100,桌機那一套
```

**一塊如果出現在手機圖上,兩個寬度都要量。**

> **這是這個專案的招牌失敗模式,這次長在「量的寬度」上:**
> 工具量得到的寬度,跟你要回答的問題所在的寬度**不一樣** ——
> 而它**不會報錯,只會給你一個乾淨的錯答案**。
>
> `block-04` 要回答的是「`:521` 的 16px 有沒有守住」。在 1100px 量,
> 答案永遠是 `14px`×29,看起來完整、一致、可信,**而且是相反的結論**。
> 跟「canvas 量到的是系統字體」、「fixture 的 key 差一個字元」同形:
> **安靜地量到了別的東西。**

## 這份文件為什麼住在 `adopt-harness/`

它原本在 `tokyo-trip/ADOPTION.md`。搬出來是因為**那個目錄同時是兩件事的範圍**,
而兩件事都被它咬到:

| | 範圍 | 症狀 |
| --- | --- | --- |
| Vercel | Root Directory = `tokyo-trip/` | 文件被部署到正式站,`GET /ADOPTION.md` 回 200 |
| Tailwind | `app.css` 的 `@source "./"` | 文件裡的字串被當成 class 編進產出 |

**第一個**:內部工作文件(失敗故事、協調規則、那五個人的相關描述)任何人打開網址就讀得到。
不是機密,但不該出現在使用者的網站上。

> 別用「README 沒事所以 .md 不會被服務」來推論 —— 實測 `GET /README.md` 是 **404**,
> 而 `GET /ADOPTION.md` 是 **200**。Vercel 對 README 有特別待遇,對別的 .md 沒有。

**第二個**:這份文件的「不要用 opacity modifier」那段字面寫著 `bg-paper/50`、`text-ink/70`,
「已登記的盲區」那段字面寫著 `backdrop-filter`。掃描器把**警告文字本身**撿去編成了 utility,
所以那三個名字真的出現在正式站的 CSS 裡(連同 `color-mix` 的 `@supports`)。
**一條叫大家不要用某個東西的規則,因為被寫下來而讓那個東西真的存在了。**

`adopt-harness/` 在版控裡但不在這兩個範圍內 —— 前一隻把工具放這裡就是為了第一個理由,
只是當時沒想到文件本身適用同一條。現在文件跟 `block-01-chip.md` 放在一起。

**推論:任何要寫進 repo 的工程文件都不要放 `tokyo-trip/` 底下。**

### 2. 時鐘要凍,而且凍的方式本身會把 app 弄壞

出發倒數(「還有 N 天」)顯示在**每一頁**的標題列。跨過午夜,九張全部「有差異」。
我第一次撞到的時候,一度以為是別人改壞的。

`fixture.py` 把時鐘凍在 `2026-09-19T03:00:00Z`。

**但第一版的凍法把整個 app 弄壞了:**

```js
function K(){ return arguments.length ? new D(arguments[0], arguments[1], ... arguments[6]) : new D(F); }
```

固定傳七個參數,所以 `new Date(ms)` 變成 `new Date(ms, undefined, ...)` —— 那是多參數
建構式,結果是 Invalid Date。`todayISO()` 一掛,開機就停住。

**症狀:每一頁都一致地空白,而截圖比對照樣報零差異。**

正確的寫法是原樣轉交:`Reflect.construct(D, arguments)`。

> 這個壞法現在是**負向對照的標準做法** —— 要測「正向斷言還活著嗎」,就把這段改回
> 固定七個參數跑一輪,九張應該全部印 `✗`。

### 5. 量字體的四個陷阱

**這一節原本不在這份文件裡。** 前面幾輪口耳相傳過三條,但沒有人寫下來 ——
`block-02-mono` 那一輪接手時是靠交接的人**口述**的,文件裡 grep 不到
`canvas`、`fonts.check`、`unicode-range` 任何一個字。現在補上,並且更正其中一條。

#### 5a. canvas 不會觸發網頁字體載入

**症狀:每個 stack 量出來的數字都不一樣,看起來很有意義,其實全是同一套字。**

`canvas.measureText()` 不會讓瀏覽器去下載網頁字體。所以你設了
`ctx.font = '14px "IBM Plex Mono"'`,量到的是**系統預設字體**,
換成別的 stack 再量,量到的還是同一套系統字體。兩邊數字有差,是因為字串不同,
不是因為字體不同。

**實際後果**:有一輪用 canvas 掃了十類字元,結論是「連全形數字和日文假名都沒動」,
而且那個結論被當成證據往上報過。`block-02-mono` 用真實 DOM 重量,
**全形數字差 2320px、全形拉丁差 1482px —— 它們確實變了**,前一個結論是假陰性。

**要用真實 DOM 渲染。** 做法見 `block-02-mono.md`:同一份 markup 用兩個 stack 各渲染一次,
每列固定高度 + `overflow:hidden`,截圖後用 `pngdiff.py` 逐像素比。

> 值得記的不只是結論。那一輪的人**讀過這份文件**,只是文件當時沒有這條 ——
> 而就算有,「知道陷阱」和「認出自己正踩在上面」也是兩件事:
> 他不覺得自己在「量字體」,他覺得自己在「掃字元」。

#### 5b. `document.fonts.check()` 要帶中文字,但帶了也還是會騙你

CJK 網頁字體按 `unicode-range` 分片送。`check()` 不帶第二參數時用的是拉丁測試字,
中文那一片還沒下載 —— **你會得到假陰性。所以一定要帶真的中文字當第二參數。**

**但這句建議只對了一半,另一半是這樣:**

```js
document.fonts.check('14px "IBM Plex Mono"', '景點')   // → true
// 而 IBM Plex Mono 一個中文字都沒有
```

`check()` 問的是「**要渲染這段文字所需要的 face 都載好了嗎**」。
當沒有任何 `@font-face` 宣告涵蓋那些碼位時,答案是「沒有東西要等」= `true`。

**它是『有沒有在等網路』的檢查,不是『涵蓋不涵蓋』的檢查。**
要知道涵蓋範圍,去讀 `@font-face` 的 `unicode-range`:

```js
document.fonts.forEach(f => console.log(f.family, f.status, f.unicodeRange))
```

#### 5c. `unicode-range` 只說得出網頁字體,說不出本機字體

讀完 `unicode-range` 也不能直接下結論。stack 裡的本機字體(`ui-monospace`/SF Mono、
`Menlo`、`PingFang TC`)**沒有 `unicode-range` 限制**,它們有沒有那個字形,
從 CSS 和 Google Fonts 的宣告裡完全看不出來。

實例:`→` U+2192 不在 IBM Plex Mono 的任何切片裡,照宣告推論「會換字體」——
**實測沒換**,因為 SF Mono 先把它接走了。

**推論的用途是「事前登記成不確定」,不是「事前下結論」。**
這也正是為什麼 CJK 後援要排在 `Menlo` **之後**:本機等寬字體沒有中文,接不住就往下落;
有些符號它們接得住,就輪不到 CJK 字體。

#### 5d. 比字體要比形狀,不要比位置

任何含座標的指標(`getBoundingClientRect().x`、元素寬度、文字換行位置)
都會把「第一個可用字體」的**度量差**算進去,也會把前面的字推走造成的位移算進去。
那量到的是版面,不是字形。

`block-02-mono` 的做法:每列固定高度 + `overflow:hidden`,
讓任何一列的差異都只代表那一列自己的字形變了。
對帳站上的差異時,也要分清楚「這個像素差是字形差,還是被前面的中文推走的」。

### 6. 這套工具自己不能兩隻同時跑

**症狀:截圖一半是你的、一半是別人的,而兩邊都沒有錯誤訊息。**

`shoot.sh` 碰的每一樣東西都是共用的:

```
PORT=8999                                  單一硬編碼的埠
rm -rf "$H/.work" && mkdir -p "$H/.work"   單一共用目錄,而且第一件事就是 rm -rf 它
build.sh → tokyo-trip/retro-modern.built.css   直接寫進共用工作樹裡被追蹤的檔
```

後跑的那隻會 `rm -rf` 掉前一隻**正在用的**工作目錄。前一隻於是對著半個目錄、
或別人的產出拍照。**這正是這整套工具存在的理由(無聲失敗),卻長在工具自己身上。**

已修:開頭用 `mkdir`(原子的)搶一把 `.lock`,搶不到就印出持有者並 `exit 2`。
`probe.sh` 共用同一把。

> **「持有 harness」是一把鎖,不只是一個習慣。** 它比「凍結 design-system」更基本 ——
> 凍結管的是相依,這條管的是工具本身。這個 repo 同時有好幾個 session 在動,
> 開跑之前先確認沒有別人在截。

#### 這個坑修了兩次,而第一次寫下的結論是錯的

```sh
trap 'rm -rf "$LOCK"; [ -n "${SRV:-}" ] && kill "$SRV" 2>/dev/null; true' EXIT INT TERM
```

**`set -e` 在 trap 裡面照樣有效**,而 `[ ] && kill` 是一個複合句 —— `kill` 失敗時整句失敗,
trap **在那裡中止**,末尾那個 `; true` 根本沒跑到。
`shoot.sh` 正常結束前會先 kill 一次 SRV,所以 trap 跑到時那個 pid **一定**是死的 ——
也就是說**它每一次成功都回傳 1**。沒人發現,是因為兩支的輸出一路都被 `| tail` 接走。

後果:`./shoot.sh a && ./shoot.sh b` 會在第一支之後停住,而訊息會說截圖失敗 —— 它明明成功了。
已改成 `if ... then kill ... || true; fi`,兩支都驗過退出碼是 0。

> **這一段的重點不是 bug,是那個「已修復」。**
>
> `block-03` 已經踩過這個坑一次 —— 在同一個檔案、距離三行的 PROVENANCE 區塊 ——
> 並且把結論寫成註解留了下來:「注意 `&&` 不能是這個區塊的最後一句」。
> 那一輪之後,這個坑在紀錄上是**修好的**。
>
> **兩件事都錯了:**
>
> 1. **範圍錯**:只修了踩到的那一句,**沒有回頭在同一個檔案裡 grep 一次同樣的形狀**。
>    三行外的 trap 裡就有一個,兩支腳本都有。
> 2. **結論錯**:那一輪留下的解法是「末尾補一個 `; true`」。
>    **實測擋不住** —— `set -e` 是在 `kill` 失敗的那一刻中止 trap 的,`true` 根本沒跑到。
>    真正有效的是把 `&&` 拆成 `if ... fi`。
>
> **一個錯的「已修復」比沒修更糟:它會讓下一個人不再看那裡。**
> 這個坑之所以活了一整輪,不是因為沒人知道它,是因為紀錄說它死了。
>
> **而它的訊號一直都在。** 退出碼從第一天起就是 1,只是兩支腳本的輸出
> 一路都被 `| tail` 之類的東西接走 —— **訊號活著,只是沒有人站在它的頻道上。**
> (這份文件裡至少有三個同形的故事:被當成噪音的 modified 產出檔、
> 永遠都在響所以沒人讀的落後警告、以及這一個。**檢查有沒有人在看,跟檢查有沒有輸出,是兩件事。**
> 後來還有兩個:被 `| grep` 濾掉的 build 錯誤,以及**發到頁尾去的使用者提示**,見第 7 條後面。)

### 7. 重編失敗會被 `| sed` 吞掉,腳本照樣往下跑、照樣說成功

**症狀:截圖用的是上一次留在樹裡的舊 `retro-modern.built.css`,而腳本回傳 0。**

```sh

`set -e` 之下**管線的結果是最後一個指令(`sed`)的結果**,永遠是 0。

> 錯誤訊息**確實印出來了**,只是混在 build 的正常輸出裡,而那一段一路被
> `| grep`、`| tail` 接走。**訊號活著,沒有人站在它的頻道上** ——
> 這份文件裡第四個同形的故事。

#### 第五個,而且這一次那個沒人站的頻道是**使用者的**

前四個都長在工具或工程流程上。第五個長在產品裡,而且是自己剛加的功能:

```js
function flash(msg) { el("sync").textContent = msg; setTimeout(renderSync, 2800); }

`#sync` 在 **`<footer>`** 裡,是頁面最底下那行 10.5px 的等寬小字。
`geocode-place-and-confirm` 那一輪加了一句「這一筆沒填地點,不會出現在地圖上」,
規則二寫得很清楚:**送出的當下是唯一講得到的時機**。
訊息確實發了,而且是站上第 32 次用 `flash()` —— 程式完全正常,探針也綠。

> **這一次「頻道沒有人站」不是比喻,是可以量的。** 修法是把那三句改寫到
> 表單旁邊那個訊息槽(用站上現成的 `.note`,不是第三套機制),
> 而驗收的斷言也跟著從「flash 有沒有講」改成「**它出現在哪裡**」——
> `getBoundingClientRect()` 比對視線落點,不是比對「有沒有出現」。

**而最該記住的是那兩條斷言本身,不是那句提示搬到哪裡。**

上一輪的探針有兩條 `flashed(/沒填地點/)`,那一輪**全部通過**;
Lulu 在真機上回報的是「送出時沒有那句提示」。

> **兩邊都沒說謊:斷言問的是「有沒有發」,使用者問的是「看不看得到」。**

前四個同形的故事都是**訊號發了,但沒有人站在那個頻道上**。
這一個多了一層:**連探針都是綠的,因為探針站的是程式的頻道,不是人的。**
把斷言改成量 `getBoundingClientRect()`,等於**把探針搬到人的頻道上** ——
**那才是修好的部分,訊息換位置只是結果。**

推論,對之後每一輪都適用:**「這個行為有沒有發生」和「這個行為有沒有到達人」
是兩個斷言。** 只寫得出前者的時候,涵蓋率要照前者報,不要照後者報。
>
> **派工的人自己認的那一半更值得記:** 上一輪的指示是「站上已經有 `flash()`,
> 優先用它,不要長第三套」。那句話是對的,但**下指示的人沒有查它把字寫到哪裡**。
> 站上那 30 幾處 `flash()` 多半是「已刪除」「刪不掉」這種操作回饋,
> 看不看得到沒那麼要緊;而這一句是要人當下就讀到的。
> **用對了機制,用錯了位置** —— 而「這個站已經有這套東西」這種理由,
> 天生就會讓人跳過「它長在哪裡」這個問題。

**已修**:兩支都改成 `if ... > .build.log 2>&1; then ... else 印出來 + exit 3; fi`。
失敗訊息會告訴你 worktree 要怎麼接 `node_modules`。兩個方向都驗過。

> **而這一條被讀過之後照樣踩了一次。** `geocode-outside-and-notice` 那一輪要驗
> 「07 的門檻升回 7 之後,舊程式會不會真的失敗」,量退出碼寫的是

> **那一輪的人讀過這一節,而且正是為了「兩個方向都要驗」才在量退出碼的。**
>
> **知道一條陷阱,跟在當下認出自己正踩在上面,是兩件事。**
> 這句話在這份文件裡已經被證實兩次了 —— 另一次是「量字體的四個陷阱」
> 那一節第 5a 條後面那句:「他不覺得自己在『量字體』,他覺得自己在『掃字元』」。
> **陷阱是按情境認出來的,不是按名字。** 所以每一條後面都要留下**症狀**,
> 不能只留下結論 —— 你下次碰到它的時候,手上只有症狀。

#### 同一輪裡這個形狀發作了第二次,而第二次是看的人自己造成的

### 8. 正向斷言掛掉時,`shoot.sh` 以前回傳 **0**

`block-04` 修掉了「每一次成功都回傳 1」,**但沒有人檢查反過來的那一半** ——
在那之後不管幾張印 `✗`,它都還是回傳 0,只印一行警告。

也就是說 `./shoot.sh a && <比對>` 會在一批「有畫面是空的」的截圖上照樣往下跑,
**而差異式檢查對兩邊都空全綠。**「最貴的一個教訓」那一節在防的東西,出口一直開著。

**已修**:`FAILED` 時 `exit 4`。健康的一批 `exit=0`、有 `✗` 的一批 `exit=4`,都驗過。

> 這是這個檔案裡第三次「修了踩到的那一半,沒有回頭問另一半」。

### 9. 位移搜尋找不到完全命中,**不一定**代表內容變了

元件的高度是小數時(例如 `.who` 的膠囊是 `64.781px`),被推到一個**小數距離**
就會換一個次像素相位,邊緣的反鋸齒跟著變,**任何整數位移都對不回去** ——
殘差長得像「有東西被改了」。

`block-05` 的對照:第三塊把 `.who` 推了 `39.344` CSS px(非整數)→ 殘差 2–3%;
第四塊推了整整 `12` CSS px(整數)→ **同一段逐位元組相同**。

**判準**:殘差集中在**邊緣**、比例零點幾到幾 %,而且同一次比對裡有另一塊完全命中
→ 那是相位。**要確定就去量幾何,不要繼續看像素** ——
`getBoundingClientRect()` 的小數點後三位一句話講完,而在像素上會繞很久。

### 10. 斷言和截圖**不是同一趟**,所以它們看的不是同一個時刻

**症狀:斷言說「只有 4 個」,而截圖裡明明有 7 個。**

`shoot.sh` 的每一張圖其實開兩次瀏覽器:一次拍照(virtual-time budget 25s 跑完的終態),
一次只為了問「畫面上真的有東西嗎」(動作之後 **900ms** 量)。
兩趟各自從零開始,所以**任何要等一次真實網路往返才會出現的東西,
可能在截圖裡有、在斷言那一刻還沒有。**

`geocode-place-and-confirm` 那一輪撞到:07 那三顆航班 pin 要等
`樂桃 MM626 · 建議起飛前 2.5 小時` 那兩次 Nominatim 回來才畫得出來(實測約 1.2s)。
以前不發作,是因為 fixture 快取裡的 pin 夠多、900ms 就過門檻了。

**處理原則:門檻只認「不靠網路就一定在」的那幾個。**
把門檻設成截圖上的數字,等於讓斷言變成網路的函數 —— 那就是「工具的陷阱 3」
(`tokyo5-pin3` 差一個字元)的形狀,只是這次長在時間上而不是 key 上。
數字因此調低的話,要**另外補一條不靠網路的斷言**把強度補回來(06 / 07 補的是 `.stop:3+`)。

> **這是這個專案招牌失敗模式的第三種長法:**
> 一次長在「量的寬度」(在 1100px 回答 390px 的問題)、
> 一次長在「量的 key」(`tokyo5-pin` vs `tokyo5-pin3`)、
> 這次長在「量的時刻」。**三次都不報錯,三次都給一個乾淨的答案。**

### 11. 量位置的時候,你量到的東西可能根本不在畫面上

**症狀:一個乾淨的數字,而它是從 0 算起的。**

`geocode-outside-and-notice` 那一輪要回答「那句提示出現在使用者看得到的地方嗎」,
而那是個幾何問題,所以用 `getBoundingClientRect()`。同一個判斷連續錯了三次,
三次都不報錯、三次都給出一個看起來很合理的數字:

| 量法 | 得到 | 為什麼是假的 |
| --- | --- | --- |
| 送出**之後**量送出鈕 | 到訊息 840 / 到頁尾 884 | 表單送出就 `hidden` 了,而 **`display:none` 的元素 rect 全是 0** —— 兩個數字都是從畫面頂端算起的絕對位置,不是距離 |
| 送出**之前**量按鈕、送出**之後**量訊息 | 到訊息 361 / 到頁尾 317 | 表單一收,底下整片往上移約一個表單的高度。**兩個位置不在同一個版面上就不能相減** —— 結論還會反過來:看起來訊息比頁尾還遠 |
| 兩個都對了,但容器是收起來的 `<details>` | 到訊息 0 / 到頁尾 **44** | 見下 |

第三個最陰:許願那一整塊住在 `<details class="wishbox">` 裡,而它預設是收起來的。
**現在的 Chrome 用 `::details-content` 的 `content-visibility:hidden` 實作收合,
不是 `display:none`** —— 裡面的元素照樣量得到一個 rect(而且有寬有高),
只是那個 rect 跟使用者看到的東西完全無關。`q("#wishbox").open` 是 `false`,
而 `getBoundingClientRect()` 給你 `{top: 839.9, width: 326, height: 58}`。

打開它之後,同一支探針量到的是 **0 / 1017** —— 訊息正好落在表單原本的位置,
而頁尾在一千像素之外。**那才是這一輪要回答的那個問題的答案。**

> **這是這個專案招牌失敗模式的第四種長法。** 前三種是量的寬度(在 1100px 回答
> 390px 的問題)、量的 key(`tokyo5-pin` vs `tokyo5-pin3`)、量的時刻(斷言和截圖
> 不是同一趟)。這一次是**量的版面** —— 而且它一次長了三種:
> 元素根本沒有盒子、兩個數字來自兩個版面、容器收起來但盒子還在。
>
> **判準**:任何 `getBoundingClientRect()` 出來的數字,先問三句 ——
> 這個元素現在畫得出來嗎?我相減的那兩個數字是同一個版面量的嗎?
> 它的祖先有沒有收起來的 `<details>` / `hidden` / `content-visibility`?
> **`rect` 是 0 不會報錯,它只會安靜地變成一個你信得過的距離。**

### 12. 「順便確認沒弄壞」的斷言,期望值常常是從當下行為抄來的

`geocode-outside-and-notice` 那一輪的探針是 114 條全綠,其中兩條長這樣:

```js
ok("地點欄本身命中表的那幾筆沒有被弄壞(成田照樣標得出來)",
  await until(function () { return /不在這裡/.test(barText()); }), barText());
ok("成田那一筆的「再查一次」照樣畫得出來(它有 pin,使用者說不對還是能按)",
  q("#map-fix-go").hidden === false, null);
```

**那兩條斷言的內容就是 bug 的樣子。** 成田的地點欄命中人工表,照那一輪自己的決定
該講「用的是人工確認過的座標」而且收起「再查一次」—— 斷言卻要求它講「不在這裡?」、
按鈕還在。寫的人以為在做迴歸保護,實際上是**跑一次、看畫面現在長怎樣、抄下來**。

> **迴歸斷言的期望值要從「決定」推出來,不是從「現況」抄下來。**
> 從現況抄的那一條,在它保護的東西壞掉的時候照樣是綠的 —— 它保護的是現況,
> 而現況裡就有那個 bug。
>
> 判準:寫「順便確認 X 沒壞」的時候問自己 **「X 該是什麼樣子,我是從哪裡知道的?」**
> 答案如果是「我剛剛看到它是這樣」,那就還沒有斷言,只有一份快照。

同一輪還有第二個形狀:**那條路一條斷言都沒有。** 11 段測的全是「標題命中」,
`kp`(地點欄命中)那條路從頭到尾沒有被走過 —— 所以 114 條綠燈裡,
Lulu 撞到的那條路的覆蓋率是 0。**「幾條斷言」不回答「哪幾條路」。**

### 13. `until()` 等的字,上一次操作可能已經留在畫面上了

`geocode-via-in-cache` 那一輪,我寫的第一版是:

```js
mm.click();
ok("...", await until(function () { return /人工確認過的表裡/.test(barText()); }), barText());
```

**上一列(桃園機場報到)講的就是那句話**,所以 `until()` 在這一列重畫之前就通過了,
後面兩條斷言量到的是**上一列的字**。探針第一次跑就把它抓出來(那條「印的是地點欄
那幾個字」掛了),否則它會變成又一個乾淨的、錯的綠燈。

> **等待條件要用「這一列才有的字」**(這裡是 `/TPE 桃園 T1/`),不要用
> 「這個狀態會講的話」。畫面上留著的舊字會讓「等到了」跟「換好了」長得一模一樣。
>
> 這是陷阱 10(斷言和截圖不是同一趟)在單一支探針**內部**的版本:
> **兩次斷言之間,畫面也不是同一個時刻。**

## 最貴的一個教訓

**差異式檢查對「兩邊都是空的」完全無感。**

工具壞掉的那次,每一頁都一致地空白,九張比對全綠。還跑了「同一狀態連跑兩次完全相同」
來證明工具是決定性的 —— **它確實是決定性的,只是決定性地壞掉。**

> **決定性是必要條件,不是充分條件。**

而且因為這個,假資料裡三筆花費**從來沒渲染出來過**,花費那頁在前幾輪一直是空白的。
接線那輪的結論沒有錯(其他八張是實的),但覆蓋率比當時報的低。
**結論對和驗證夠強是兩件事。**

#### 收緊過的四條,以及為什麼

負向對照的第一次結果是**九張裡有三張漏接** —— app 已經死到標題列印 `NaN 天`、
行程花費許願全空,07 / 08 / 09 還是印 `✓`。原因各不相同:

- **08**:`#stop-form input` 量的是**靜態 markup**。那三個 input 本來就寫在 HTML 裡,
  app 開不開機都在;而且 `#stop-form` 預設帶 `hidden`,表單根本沒打開也算數
- **09**:同上,而且更嚴重 —— 09 的動作是 `d.querySelector('[data-edit-stop]').click()`。
  app 死掉時根本沒有 `[data-edit-stop]`,這行丟例外、被 `try/catch` 吃掉、
  **對話框從頭到尾沒開過,而斷言還是過。那條斷言從來沒有驗到它名義上要驗的東西。**
- **07**:門檻 2 太低。app 死掉時航班那兩個寫死的成田機場點照樣畫得出來
  (走 `OUTSIDE` 硬表,不經過 app 的資料層),剛好湊到 2

教訓:**斷言要挑「只有 app 真的跑起來才會存在」的東西。** 靜態 markup 不算。
量「容器開了沒」(`:not([hidden])`)比量「裡面有幾個 input」誠實。

#### 解析器自己的坑

斷言字串原本是 `spec.split(":")` 取 `p[1]` 當門檻。選擇器裡只要出現 `:not()`
這種偽類,門檻就會被切成字串,`parseInt` 得 `NaN`,而 **`n < NaN` 永遠是 false** ——
斷言不報錯,只是從此不再檢查任何東西。上面要加的 `:not([hidden])` 剛好會踩到。

已改成從**最後一個**冒號切,而且門檻讀不出數字時明確報錯。
**這個專案的招牌失敗模式,那次是埋在檢查器自己的字串解析裡。**

#### 涵蓋範圍到哪裡

負向對照只做了「app 完全沒開機」這一種壞法。**沒有**測「只有某一塊 CSS 沒生效」
那種局部壞法 —— 正向斷言本來也不是為那個設計的(那是差異式檢查的工作)。
全部是 headless Chrome,沒跑過真實裝置或真實 Safari。
(唯一的例外是第四塊那次由 Lulu 在 iPhone 上做的對焦測試,見上面那一節 ——

> **而「沒跑過真實 iOS」這一句在第四塊變成了一個具體的欠款,後來由人還掉了。**
> 那一塊整個決定(保留 `:521` 的 16px)就是為了防 iOS Safari 對焦放大,
> **而這套工具在定義上驗不到它** —— 能證明的只有「觸發條件不成立」(font-size 是 16px),
> 不是「行為沒發生」。見最上面「第四塊留下一件要真人做的事」。
> **有人要拿 iPhone 點一下。**

## 驗收規則

**兩套規則,看那一輪該不該改變外觀。**

### 不該改變外觀的輪(包 layer、接線)

零差異。**任何非零一律當成問題查,不准先歸因到任何已知效應。**

「帶著預期去驗收」會讓第一反應變成歸因而不是追查,那就毀掉驗收的意義。

### 該改變外觀的輪(每一塊轉換)

零差異反而代表沒生效。所以:

1. **動手前**先寫下預期會產生哪些視覺變化,逐項寫進 `block-NN-*.md`
2. 比對後,把實際差異逐一對到清單上
3. **清單外的差異是問題**,不管看起來多合理
4. **清單上有、但實際沒出現的也是問題** —— 那代表你以為會生效的東西沒生效
5. **「我驗不到這個」也要查證過再寫。** 把涵蓋率**報低**看起來保守無害,
   實際上是放棄一個其實有效的驗證管道
6. **逐條列完改動之後,再寫一行「這些合起來,使用者會看到什麼」。**
   前五點管的是「每一條改動對不對」,這一條管的是「它們湊在一起的那個結果有沒有人想過」

第 4 點容易被忽略。前面幾輪一直在防「不該變的變了」,轉換開始之後要同時防「該變的沒變」,
而後者在 CSS 裡一樣不報錯。

**第 6 點是連續兩輪同一種登記不足之後補的,不是個案。**

| 輪 | 逐條登記的 | 實際發生的 |
| --- | --- | --- |
| `geocode-place-and-confirm` | V5「剩下的 pin 座標不動,標籤可能讓位」 | 座標確實沒動,但**取景整個換了** —— 主角從兩個點變成一個點,`fit.length > 1` 不成立,06 變成以橫濱為中心 |
| `geocode-outside-and-notice` | K3(標題也算人工表候選)、K5(`pinOf` 同序)、K6(再查一次先查表)三條各自都對 | **三條合起來** = 「查無之後,人工表會從標題接手」,那顆 pin 換座標而不是消失 —— 上一輪的探針因此有一條必須改寫,而預期表裡沒有它 |

兩次都不是「哪一條寫錯了」,是**沒有人把逐條的結果乘起來**。
兩次都被抓到,也都是自己回頭發現的 —— 但**發現的時機都是「探針紅了」或「圖變了」之後**,
那已經是事後歸因了,而這一節開頭就寫著事前登記和事後歸因的差別。

> **寫法很便宜:逐條表格底下補一句「所以使用者會看到 ____」。**
> 答不出來,就是那幾條你其實只推到一半。

第 5 點是 `block-04` 那一輪自己撞到的:事前登記寫了「`:focus-visible` 這一輪驗不到
(截圖不對焦)」,**而 08 的第一個欄位在截圖裡就是對焦的** —— app 自己 focus 了它。
那一輪剛好在同一個地方發現一個真的回歸(對焦時圓角 8px→4px),
**如果當時信了自己那句「驗不到」,那張圖就不會被拿來看。**

> **登記不準有兩個方向,而低估的那個方向感覺起來像謙虛。**
> 「我驗不到」跟「我預期它會變」一樣是一個斷言,一樣要有根據 ——
> 最便宜的根據就是**把那張圖切出來看一眼**。

已知且無法消除的差異,要在**該輪開始之前**登記。事前登記和事後歸因看起來像同一件事,
但前者可以被檢驗、後者不能。

`block-01-chip.md` 是完整的範本:為什麼挑這塊、預測表、實際結果、偏離的解釋。

## 怎麼挑一塊

- **最小、最獨立、最容易單獨看到**
- **而且 design-system 裡要有語意對得上的組件**
- **而且不要卡在別人還沒修的東西上**
- **而且要問一句:它出現在哪一張截圖裡?**

第二個判準比第一個重要。挑一塊在 design-system 裡沒有對應組件的,就會變成
「用 utility 手工拼出一個外觀」—— 那驗不到我們要驗的東西(組件在真實頁面上長得對不對)。

第三個曾經擋掉三塊:`rm-chip`、`rm-overline`、`rm-day-pin` 都吃 `--font-mono`,
而當時 mono 沒有 CJK fallback。**那個阻礙已經解除**(`block-02-mono` 補在
**tokyo-trip 自己的 `:root`** 上,不是 design-system 那一份)。

### 動手之前還要做一件事:把要刪的那條規則**整條**盤完

**這四塊每一塊都是「刪掉一條舊規則、換上一個組件 class」,而舊規則幾乎都是
後代選擇器** —— `.fld label`、`.fld input`、之後還會有別的。
後代選擇器選到的東西**比你腦子裡那份清單多**,而且它**整條**的宣告都作用在那些東西上。

`block-05` 拿新截圖回頭驗第三塊的時候量到這件事:

> `.who label` 住在 `.fld` 裡,所以 `.fld label` **整條**都作用在十顆成員膠囊上。
> 第三塊只登記了 `color` 和 `letter-spacing` 兩項並且原樣補了回去 ——
> **結論是對的,但支撐它的推理不完整。**
> 沒出事是因為 `.fld label` 的 `font-weight`(`400`)和 `margin-bottom`(`0px`)
> **剛好等於瀏覽器預設**,規則刪掉之後落回原處。
> 舊規則要是寫了 `font-weight:600`,**十顆膠囊的字重會在無人登記的情況下被改掉,
> 而九張截圖一樣看不到。**

**所以做法是:把那條規則的每一個宣告列出來,逐個問「它作用在哪些元素上」,
而不是只盤你打算改的那幾個。** 差別在於前者會把「刪掉之後會落回什麼」
變成一個你答得出來的問題。

> 這是這個專案那條招牌教訓的又一次發作:**結論對和方法對是兩件事。**
> (同一頁上還有另外兩個:「同一狀態連跑兩次相同」證明不了工具沒壞、
> 「成功要回傳 0」驗過了不代表「失敗要回傳非零」也驗過了。)

#### 反過來的那一半:**加**一條規則也要問它連帶關掉了誰

上面那一段講的是「刪一條規則,會讓一堆被它遮住的宣告浮出來」。
`geocode-outside-and-notice` 那一輪撞到的是**同一件事的鏡像**,而且代價更直接:

> 規則一(「沒填地點就不查,標題不再是候選」)是對的 —— 拿標題去問一個
> 不知道自己不確定的服務,就是那顆雲南 pin 的成因。
> 但實作是把 `item.place` 傳給 `pinFor()`,而 `pinFor()` **同時**是
> `OUTSIDE` 那張人工確認過的表的入口。標題一從候選裡拿掉,
> **人工表也跟著比對不到了** —— 而那張表是整條路上最準的一環。
>
> 結果:`{ title:"桃園機場 第一航廈 報到", place:"樂桃 MM626 · 建議起飛前 2.5 小時" }`
> 掉到線上查詢,拿一句航班備註去問;而「再查一次」那條路**從來就沒查過那張表**,
> 按下去只是拿另一個線上結果蓋掉,錯得更確定。

**一條規則的正面效果,連帶砍掉了一個它沒看見的受益者。**
上一輪還為這件事寫了一條「✅ `OUTSIDE` 不受誤傷,而且驗過」——
它檢查的是「六個航班節點有沒有填地點」(有),該問的是
「**填的那個東西比對得到表嗎**」(有一筆比對不到)。**問錯的問題會拿到一個乾淨的綠燈。**

> **做法**:要收掉一個候選字串、一個選擇器、一個輸入來源之前,
> 先 `grep` 它**還通往哪裡**。這裡只要 `grep -n OUTSIDE` 就看得到三個消費者
> (地圖的 `pinFor`、天氣的 `resolvePlace` 和 `stopWx`),
> 而「地圖那條的入口同時是人工表的入口」在那一眼就看得出來。

**第六塊(`.who`)正好要面對同一個結構** —— 這次是 `.who input` 那四個
第四塊補回去的宣告,以及 `:537` 的 `.who label` 手機覆寫。見下面「第六塊」。

**第四個判準是 `block-03-label` 那一輪學到的。** 那一塊改了 32 個標籤,
**九張截圖只看得到 9 個**,其餘 23 個躲在沒有被打開過的表單和對話框裡。
不是不能做,但要**事前就知道自己驗得到多少**,並且在該輪的
「沒有驗到的事」裡寫清楚 —— 而不是做完才發現覆蓋率只有三成。
挑一塊之前,先對著九張截圖問:**這一塊會出現在哪幾張?**

可用的組件(`design-system/retro-modern.css` 的 `@layer components`):

```
rm-base  rm-btn(--action/--cta/--ghost/--lg/--secondary/--sm/--steel)
rm-card(--arch/--expressive/--raised/--surface)  rm-chip(--accent/--solid)
rm-day-pin  rm-divider(--dashed)  rm-input  rm-label  rm-overline
rm-row  rm-stack  rm-toast
```

### 第六塊:`.who` 那一整組 —— 擋了兩輪的理由已經消失

`#exp-form` 和 `#exp-edit-overlay` 現在有截圖了(`10-exp-form` / `11-exp-edit-dialog`),
所以「沒有畫面就驗不了」不再成立。**`.who` 是現在最該做的一塊,理由不只是輪到它:**

**十顆成員膠囊是壞的,而且看到圖才看得出來有多壞。**
`.who input` 的 `width:100%` 把 13px 的原生核取方塊撐成 **27.53px**,
在一顆 82px 寬的膠囊裡吃掉三分之一,**「阿輝」「佳瑜」「志偉」「雅倫」全部被擠成兩行**
(只有單字的「媽」沒事),膠囊因此高 **64.781px** —— 比旁邊 48px 的輸入欄位還高。

它的來源是被刪掉的那條 `.fld input{width:100%}`(本來是給文字欄位用的),
`.who` 住在 `.fld` 裡所以一起被選到,第四塊為了讓那一輪零改變又**原樣補了回去**。
`block-04` 當時寫「看起來就是個意外」—— 看到圖之後可以把「看起來」拿掉了。

動它之前要知道的(**先讀上面「把要刪的那條規則整條盤完」,這一塊正是那個結構**):

1. **`.who input` 有四個宣告是第四塊補回去的**(`width` / `background` /
   `font-size` / `line-height`)。`width:100%` 該走,另外三個要當成同一個決定一起想。
2. **`.who label` → `rm-chip`** 語意對得上(它就是一顆膠囊)。但 `:537` 有一條
   `.who label{padding:9px 13px; font-size:14px}` 的手機覆寫,特異度(0,1,1)
   **會贏過 `.rm-chip`(0,1,0)** —— 跟第四塊 `:521` 那題一模一樣的形狀,
   留不留要**事前**決定,不要做完才發現手機上沒換到。
3. `probes/who.js` 已經在那裡了,`WIDTH=390` 和 `WIDTH=1100` 兩個都要跑。
4. 這一塊**同時出現在 10 和 11 兩張圖上**,而且兩張都畫得到 ——
   **這是第一次「要改的東西」和「看得到它的截圖」完全對得上。**

細節和量到的每一個值見 `block-05-expform-shot.md`。

### 第五塊做了什麼,以及它為什麼算一塊

**它一個樣式都沒改。** 產出是兩張截圖,加上拿那兩張回頭驗證
第三塊和第四塊各自「刻意凍住」的 `.who`。結論:**凍住守住了** ——
膠囊和核取方塊的每一項 computed 值、連小數點後三位的幾何都相同,

兩件值得帶走的事:

- **第三塊沒有漏,但那是運氣。** 前兩個人報的結論是對的,支撐它的推理不完整。
  **已經提到這一節上面「把要刪的那條規則整條盤完」去了** —— 那條對之後每一塊都適用,

### 第四塊實際做了什麼(已完成,細節見 `block-04-input.md`)

- **`.fld input`(0,1,1)高過 `.rm-input`(0,1,0)**,跟載入順序無關。

  > **找這種東西的方法是量,不是讀。** `:focus-visible` 那條是探針的離群值報出來的,
  > 讀 CSS 的時候完全沒想到。

## 約束

### 不要用 opacity modifier

`bg-paper/50`、`text-ink/70` 這一類。它們編出來是 `color-mix`,**在 iOS 16.3 以下
整條宣告無效** —— 不報錯,背景就是不上色。

Lulu 對 iOS 版本的答覆是「以最新版為主」,那是**假設不是事實**(她沒有去問那四個人)。
避開這類 utility 就避開了這個假設的主要暴露面。需要半透明就用明確色值或自己的 `:root` 變數。

### `<link>` 必須在 `<style>` 之前

不是保險,是**必要條件**。兩邊的組件都在 `components` 層,同層之內比特異度再比原始碼順序,
**後載入的贏**。design-system 先載入,`.card` 才蓋得過 `.rm-card`。

反過來的話它的組件會開始無聲蓋掉這邊寫好的東西。

### `:root` 留在 `@layer components` 外面

自訂屬性一旦進了層,任何無層級的 `:root` 都蓋得過它。留在外面就永遠是這邊說了算 ——
那也是之後想覆寫 design-system 某個 token 時唯一有效的位置。

> **這條同時是保護傘和阻礙,而後半段害過一次。**
> 「永遠是這邊說了算」的另一面是:**design-system 對同一個 token 的修正永遠到不了這裡。**
> 實際發生過 —— `--font-mono` 缺 CJK 後援,有人去修了 design-system 那一份,
> 重編之後九張零差異,因為 tokyo-trip 的 `:root` 擋著,那個修正從來沒到達任何元素。
>
> **要查一個 token 現在是誰說了算,不要讀 CSS 猜,直接在真實 DOM 上問:**
>
> ```js
> getComputedStyle(document.documentElement).getPropertyValue('--font-mono')
> ```
>
> 兩邊的 token **同名而且值長得很像**,分辨的方法是**只看第一個字體名**。
> 完整的辨識表和那次繞路的經過,寫在
> `block-01-chip.md` 的「怎麼分辨這個 computed 值是誰的 stack」。

### 改 markup 之後一定要重編

Tailwind 是 content-driven,掃 `tokyo-trip/` 決定編出哪些 utility。
用了新 class 沒重編 = 那個 class 不存在 = 樣式安靜消失。

**已經做進 `shoot.sh` 了**,截圖前自動重編,不是人要記得的事。

## 已登記的盲區

產出的 `utilities` 層有 8 個 class:

```
block  ease-out  filter  hidden  inline  resize  sticky  transform
```

**沒有一個是 markup 在用的。** 掃描器從 CSS 屬性值、JS 字串、**甚至中文註解**裡撿出來的:
`padding-block`、`position:sticky`、`cursor:col-resize`、`backdrop-filter`、
還有註解裡寫的「用 clip 不用 hidden」。

**後果:這 8 個名字不受「忘了重編」偵測保護。** 哪天想拿其中一個當 utility 用
(例如 `class="hidden"`),它早就在產出裡了,忘記重編也不會被抓到。

不修:為了 8 個常見字去調掃描規則,成本高於收益。詳見 `tokyo-trip/app.css` 的註解。

### 它曾經變成 11 個,而原因是這份文件自己

`9262c9a`(把這份文件寫出來的那個 commit)之後,重編一次會多出三個:

```
backdrop-filter   bg-paper\/50   text-ink\/70
```

因為當時這份文件住在 `tokyo-trip/`,而它的「不要用 opacity modifier」那段
字面寫著 `bg-paper/50` 和 `text-ink/70`、「已登記的盲區」那段字面寫著 `backdrop-filter`。
**掃描器把警告文字本身撿去編成了 utility。**

連帶的第二個症狀:`tokyo-trip/retro-modern.built.css` 是在這份文件進 repo **之前**編的,
所以從那時起 git 裡的產出就跟它的原始碼對不上了 —— **任何人跑一次 `shoot.sh`
都會讓它變成 modified**,而那看起來像是自己不小心改到的。

把文件搬到 `adopt-harness/` 之後重編,產出回到 8 個 class,而且跟 `9262c9a` 裡那份
**逐位元組相同**。這個故事比結論有價值:
**掃描範圍的邊界不只約束程式碼,也約束你寫在那個資料夾裡的每一個字。**

### 而上面那句「跑一次就會變 modified」害過一次,要更正

那個症狀當時是真的(產出跟原始碼對不上),搬走文件之後**已經不成立**了。
但那句話留在這裡,而且它做的事比過期更糟:

`design-system/` 一髒,`tokyo-trip/retro-modern.built.css` 就會跟著變。
那個檔在舊版出處紀錄的範圍內 —— 換句話說,**「凍結被打破了」這件事一直有一個訊號,
而這份文件親手把那個訊號標成了噪音。**

> **那比「紀錄範圍太窄」嚴重得多。範圍窄是遺漏;教人忽略,是主動拆掉一道還在運作的防線。**

現在的出處紀錄會單獨列出相依的狀態,不必再靠產出檔去推。
但這件事值得記住,因為它會再發生:**在文件裡寫「這個訊號可以忽略」之前,
先確認它真的只有噪音的意思。**

## 多 session 協調規則

這個 repo 同時有別的 session 在動(`design-system/` 由另一隻負責),共用**同一個工作樹**。

- **提交前先問協調者**(`playground-8b`)。編輯可以並行,提交不行
- **逐檔 `git add`,不要用 `-A` 或 `.`** —— 會把別人手上的檔案掃進去。
  我實際遇過一次:協調者放行時說工作樹只有我的檔,我 add 之前重讀,
  發現另一隻已經落盤了兩個檔。**放行不等於工作樹狀態的保證,自己重讀。**
- **`DECISIONS.md` 一次只有一隻能寫**,要先拿鎖
- **一輪轉換進行中,design-system 凍結**。相依一動,差異就無法歸因。
  開始一塊之前跟協調者說,做完回報才解凍。
  **現在出處紀錄會單獨記相依的狀態**,凍結有沒有被打破,事後查得到
- **同一時間只有一隻能持有 harness**(`shoot.sh` / `probe.sh`)。
  它們共用 `.work/`、共用埠、共用產出檔 —— 腳本自己有鎖會擋,但排隊還是要先講。
  見「工具的陷阱 6」
- **開工前先問協調者「現在有誰在動哪裡」**。實際發生過:兩隻 session 被指派了
  **同一塊**,差四分鐘,兩邊都要改 `tokyo-trip/index.html` 和同一份 `block-03-label.md`。
  擋下來的不是工具,是**動手之前先回報**這個習慣

### 一塊一個人(Lulu 在第三塊之後定的)

**每完成一塊、提交之後,那個 worker 更新這份文件,然後換下一個人接。
不等 session 的上下文用完,在自然的邊界換手。**

理由:上一隻(Tokyo trip)的上下文用完時卡在半途,**而且不是它自己發現的**,
是 Lulu 看到才講的。

> **session 看不太到自己還剩多少**,所以「滿了就換」沒有可靠的觸發器 ——
> 那正是這個專案一路在拆的那種「靠人注意」的機制。
> 換成**事件觸發**(一塊做完)就不需要偵測狀態了。

附帶的好處:**這份文件每一塊都會被真的用一次。** 它的缺口就是這樣被挖出來的 ——
`block-02-mono` 那一輪挖出「量字體的四個陷阱」沒有寫下來,
`block-03-label` 那一輪挖出出處紀錄看不到相依、harness 不是併發安全的。
**沒有換手就沒有這些。**

接手的人要做的第一件事,見最上面「現在做到哪」的三行指令 —— 先問線上是什麼,
再讀這份文件,**然後自己重截一次基準用 `cmp` 驗過**再開工。
