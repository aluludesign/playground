## 工具:`adopt-harness/`(這份文件的同一個資料夾)

> 它在 repo 裡,但**不在 Vercel 的部署範圍、也不在 Tailwind 的掃描範圍**
> (兩者都是 `tokyo-trip/`)。
>
> 它原本放在 repo 外面。搬進來的理由:換手之後沒有人重建得出它 ——
> 裡面每一行幾乎都是踩到坑之後補的,從零寫一份不會長這樣。

```

probe.sh        在真實 DOM 上量東西,跑 probes/*.js,結果以 JSON 印出
                **WIDTH=390 ./probe.sh ...** 在手機寬度量(預設 1100,見下)
probes/         探針腳本。labels.js 是範本:盤點 + 逐項 computed 值 + 離群值
                inputs.js 會先用真實點擊把 08/09/花費那幾個表單打開再量
                dayscroll.js 診斷 01 的雙穩態(非決定性來源 #3)
fixture.py      固定的假資料 + 凍結時鐘
pngdiff.py      逐像素比對,回報差異位置與**列群**
crop.py         把兩張圖的同一段 y 並排切出來,中間畫紅線 —— 用眼睛確認
wrap-layer.py   一次性的,把內嵌樣式包進 @layer components(已經用過了)
shots/          產出,不進版控(一組約 1.8MB,每輪重生)
block-01-chip.md  第一塊的預測清單 + 實際結果,可以當範本
block-02-mono.md  mono 中文後援那一輪(不是組件轉換,是修回歸)
block-03-label.md 第三塊,附兩個工具缺口的修法與驗證
block-04-input.md 第四塊,附 01 雙穩態的根因與兩個 harness bug
ADOPTION.md     這份
```

**`shoot.sh` 和 `probe.sh` 共用一把鎖,同一時間只有一隻跑得動。** 見「工具的陷阱 6」。

`probe.sh` 跟 `shoot.sh` 站在同一個地基上(同樣先重編、同樣灌 `fixture.py`),
所以**探針量到的數字和截圖是同一個世界**。沒有這一點,兩邊對不上帳。

用法:

```sh
cd <repo>/adopt-harness          # 注意:是 repo 根目錄,不是 tokyo-trip/ 底下
./shoot.sh <標籤>                 # 截一組,放進 shots/<標籤>/
python3 pngdiff.py shots/a/01-plan-mobile.png shots/b/01-plan-mobile.png
```

`shoot.sh` 會**自動先重編** design-system 的產出,不用手動跑 build。

**`probe.sh` 預設在 1100px 量,而九張截圖裡有七張是 390px。**
`index.html` 有一整段 `@media (max-width:640px)` 的覆寫,在 1100 量到的是那七張
**根本看不到的那一套值**。`block-04` 差點因此下相反的結論(見那一份的「新踩到的陷阱 3」)。

```sh
WIDTH=390 ./probe.sh probes/inputs.js     # 08 / 09 實際的寬度
./probe.sh probes/inputs.js               # 1100,桌機那一套
```

**一塊如果出現在手機圖上,兩個寬度都要量。**

> **這是這個專案的招牌失敗模式,這次長在「量的寬度」上:**
> 工具量得到的寬度,跟你要回答的問題所在的寬度**不一樣** ——
> 而它**不會報錯,只會給你一個乾淨的錯答案**。
>
> `block-04` 要回答的是「`:521` 的 16px 有沒有守住」。在 1100px 量,
> 答案永遠是 `14px`×29,看起來完整、一致、可信,**而且是相反的結論**。
> 跟「canvas 量到的是系統字體」、「fixture 的 key 差一個字元」同形:
> **安靜地量到了別的東西。**

## 這份文件為什麼住在 `adopt-harness/`

它原本在 `tokyo-trip/ADOPTION.md`。搬出來是因為**那個目錄同時是兩件事的範圍**,
而兩件事都被它咬到:

| | 範圍 | 症狀 |
| --- | --- | --- |
| Vercel | Root Directory = `tokyo-trip/` | 文件被部署到正式站,`GET /ADOPTION.md` 回 200 |
| Tailwind | `app.css` 的 `@source "./"` | 文件裡的字串被當成 class 編進產出 |

**第一個**:內部工作文件(失敗故事、協調規則、那五個人的相關描述)任何人打開網址就讀得到。
不是機密,但不該出現在使用者的網站上。

> 別用「README 沒事所以 .md 不會被服務」來推論 —— 實測 `GET /README.md` 是 **404**,
> 而 `GET /ADOPTION.md` 是 **200**。Vercel 對 README 有特別待遇,對別的 .md 沒有。

**第二個**:這份文件的「不要用 opacity modifier」那段字面寫著 `bg-paper/50`、`text-ink/70`,
「已登記的盲區」那段字面寫著 `backdrop-filter`。掃描器把**警告文字本身**撿去編成了 utility,
所以那三個名字真的出現在正式站的 CSS 裡(連同 `color-mix` 的 `@supports`)。
**一條叫大家不要用某個東西的規則,因為被寫下來而讓那個東西真的存在了。**

`adopt-harness/` 在版控裡但不在這兩個範圍內 —— 前一隻把工具放這裡就是為了第一個理由,
只是當時沒想到文件本身適用同一條。現在文件跟 `block-01-chip.md` 放在一起。

**推論:任何要寫進 repo 的工程文件都不要放 `tokyo-trip/` 底下。**

## 工具的陷阱(全部是踩出來的)

### 1. 它截的是「工作目錄現況」,不是某個 tag

**症狀:比對永遠通過。**

我做過一次:改完 `index.html` 之後才想到要截基準,結果截出來的「基準」是改動後的版本,
拿去跟改動後比,當然零差異。

**要截某個 commit 的樣子,先 `git stash` 你的改動。**

每組截圖旁邊有 `PROVENANCE.txt`,記了截圖當下的 HEAD、**整個 repo** 有幾個檔沒提交、
其中幾個會被烘進圖(`tokyo-trip/` 與 `design-system/`)、相依的 HEAD 與髒不髒、stash 幾筆。
事後回頭看得出這批是站在哪裡截的。

> **它以前只數 `tokyo-trip/`。** `git -C "$SRC" status --porcelain -- .` 的 `-- .`
> 把範圍限死在那個目錄,而 build 是從 `design-system/` 編出來的 ——
> 「一輪進行中 design-system 凍結」那條規則因此長期**沒有任何儀器在背後撐著**。
> `block-03-label` 那一輪修好,並且故意留一個髒改動驗過它真的會講出來。

### 2. 時鐘要凍,而且凍的方式本身會把 app 弄壞

出發倒數(「還有 N 天」)顯示在**每一頁**的標題列。跨過午夜,九張全部「有差異」。
我第一次撞到的時候,一度以為是別人改壞的。

`fixture.py` 把時鐘凍在 `2026-09-19T03:00:00Z`。

**但第一版的凍法把整個 app 弄壞了:**

```js
function K(){ return arguments.length ? new D(arguments[0], arguments[1], ... arguments[6]) : new D(F); }
```

固定傳七個參數,所以 `new Date(ms)` 變成 `new Date(ms, undefined, ...)` —— 那是多參數
建構式,結果是 Invalid Date。`todayISO()` 一掛,開機就停住。

**症狀:每一頁都一致地空白,而截圖比對照樣報零差異。**

正確的寫法是原樣轉交:`Reflect.construct(D, arguments)`。

> 這個壞法現在是**負向對照的標準做法** —— 要測「正向斷言還活著嗎」,就把這段改回
> 固定七個參數跑一輪,九張應該全部印 `✗`。

### 3. fixture 的 localStorage key 必須跟 app 一字不差

**症狀:看起來一切正常,但那一頁其實是網路的函數。**

`fixture.py` 灌的是 `tokyo5-pin`,而 `index.html` 讀的是 **`tokyo5-pin3`**
(第 1700 行,`const PINLS`;它的註解自己寫了「換過 key 兩次」)。

**差一個字元,不會報錯**,只是整份圖釘快取失效 → `pinFor()` 改走 Nominatim 線上查詢
(每筆之間還 sleep 1100ms 避開速率限制)→ 地圖上有幾個 pin、pin 在哪,
完全看網路那一刻多快、Nominatim 回什麼。

後果不是「少幾個 pin」,是 **06 / 07 兩張圖從來就不是決定性的**。
`block-01-chip.md` 寫「其他八張逐位元組相同」—— 那個結論在當時成立,
但**成立是運氣**(兩組截圖差一分鐘截的,Nominatim 剛好回一樣的東西)。
30 分鐘後再截,07 就跟 `block01` 差了 0.21% 的像素,全落在地圖區。

已修(key 改成 `tokyo5-pin3`)。修完的驗證方式是**加 `--host-resolver-rules` 把
localhost 以外的網路全部切斷重跑,確認數字一模一樣** —— 只看「數字變好了」不算驗證。

| `tokyo5-v1` | `LS` | ✅ |
| `tokyo5-wx` | `WXLS` | ✅ |

### 4. 非決定性來源

#### 01-plan-mobile 是雙穩態的(`block-04` 發現)

**同一個乾淨工作樹連跑兩次 `shoot.sh`,01 會得到兩張不同的圖。** 根因量過了:

`renderDays()` 最後一行是 `cur.scrollIntoView({inline:"center"})`,它算出來的 `scrollLeft`
取決於**算的那一刻每張日卡多寬**,而日卡寬度取決於 Noto Sans TC 載完了沒。
沒載完 = 用後援字體的度量(卡片約 107px),載完之後卡片縮到 101px,
**但 `scrollLeft` 不會重算**。偶爾字體先贏那場賽跑,就得到另一張圖。

```
診斷: WIDTH=390 ./probe.sh probes/dayscroll.js
  實際 scrollLeft 102 / 以現在的度量重算 88 / 反推當初的卡寬 106.8(現在 101)
```

**沒有消掉,而且是刻意的。** 兩個狀態都是使用者真的會看到的(第一次造訪 vs 字體在快取裡),
要「消掉」就得讓 harness 在字體載完之後強制重捲一次 —— **那會改掉 01 這張圖本身,
前面每一組基準都不能再比**,代價遠大於收益。

> **遇到它的判準**:01 的差異如果剛好是 `2.1481%` / `y=454..651` / **1 群** /
> 水平位移 27,就是這件事,**重截一次會回到相同**。
> **任何其他形狀的差異都要當成問題查** —— 不要把這一條當成「01 可以忽略」。
> (這份文件有前科:見「已登記的盲區」最後那一節,把訊號標成噪音是怎麼拆掉一道防線的。)

> 前面那句「前兩個都只影響『變化過程』和『外部資源』,不影響我要驗的版面」
> **對地圖不成立**。決定 pin 座標的是查詢結果,而 pin 座標就是版面 ——
> pin 一移動,`layoutLabels()` 的碰撞結果跟著變,標籤會改放到下面、或直接被藏起來。

**`tokyo5-geo` 還沒灌。** 那是天氣用的地名查詢快取。實測「斷網 vs 連網」跑首頁,
六張日卡的天氣字串**完全相同**,所以現在不影響版面 —— 但那是因為目前的假資料裡
沒有東京都以外的地點(`resolvePlace()` 對東京都的結果一律 `null`,走預設座標)。
**哪天假資料加一筆箱根或橫濱,它就會變成第三個非決定性來源。** 事前登記在這裡。

### 5. 量字體的四個陷阱

**這一節原本不在這份文件裡。** 前面幾輪口耳相傳過三條,但沒有人寫下來 ——
`block-02-mono` 那一輪接手時是靠交接的人**口述**的,文件裡 grep 不到
`canvas`、`fonts.check`、`unicode-range` 任何一個字。現在補上,並且更正其中一條。

#### 5a. canvas 不會觸發網頁字體載入

**症狀:每個 stack 量出來的數字都不一樣,看起來很有意義,其實全是同一套字。**

`canvas.measureText()` 不會讓瀏覽器去下載網頁字體。所以你設了
`ctx.font = '14px "IBM Plex Mono"'`,量到的是**系統預設字體**,
換成別的 stack 再量,量到的還是同一套系統字體。兩邊數字有差,是因為字串不同,
不是因為字體不同。

**實際後果**:有一輪用 canvas 掃了十類字元,結論是「連全形數字和日文假名都沒動」,
而且那個結論被當成證據往上報過。`block-02-mono` 用真實 DOM 重量,
**全形數字差 2320px、全形拉丁差 1482px —— 它們確實變了**,前一個結論是假陰性。

**要用真實 DOM 渲染。** 做法見 `block-02-mono.md`:同一份 markup 用兩個 stack 各渲染一次,
每列固定高度 + `overflow:hidden`,截圖後用 `pngdiff.py` 逐像素比。

> 值得記的不只是結論。那一輪的人**讀過這份文件**,只是文件當時沒有這條 ——
> 而就算有,「知道陷阱」和「認出自己正踩在上面」也是兩件事:
> 他不覺得自己在「量字體」,他覺得自己在「掃字元」。

#### 5b. `document.fonts.check()` 要帶中文字,但帶了也還是會騙你

CJK 網頁字體按 `unicode-range` 分片送。`check()` 不帶第二參數時用的是拉丁測試字,
中文那一片還沒下載 —— **你會得到假陰性。所以一定要帶真的中文字當第二參數。**

**但這句建議只對了一半,另一半是這樣:**

```js
document.fonts.check('14px "IBM Plex Mono"', '景點')   // → true
// 而 IBM Plex Mono 一個中文字都沒有
```

`check()` 問的是「**要渲染這段文字所需要的 face 都載好了嗎**」。
當沒有任何 `@font-face` 宣告涵蓋那些碼位時,答案是「沒有東西要等」= `true`。

**它是『有沒有在等網路』的檢查,不是『涵蓋不涵蓋』的檢查。**
要知道涵蓋範圍,去讀 `@font-face` 的 `unicode-range`:

```js
document.fonts.forEach(f => console.log(f.family, f.status, f.unicodeRange))
```

#### 5c. `unicode-range` 只說得出網頁字體,說不出本機字體

讀完 `unicode-range` 也不能直接下結論。stack 裡的本機字體(`ui-monospace`/SF Mono、
`Menlo`、`PingFang TC`)**沒有 `unicode-range` 限制**,它們有沒有那個字形,
從 CSS 和 Google Fonts 的宣告裡完全看不出來。

實例:`→` U+2192 不在 IBM Plex Mono 的任何切片裡,照宣告推論「會換字體」——
**實測沒換**,因為 SF Mono 先把它接走了。

**推論的用途是「事前登記成不確定」,不是「事前下結論」。**
這也正是為什麼 CJK 後援要排在 `Menlo` **之後**:本機等寬字體沒有中文,接不住就往下落;
有些符號它們接得住,就輪不到 CJK 字體。

#### 5d. 比字體要比形狀,不要比位置

任何含座標的指標(`getBoundingClientRect().x`、元素寬度、文字換行位置)
都會把「第一個可用字體」的**度量差**算進去,也會把前面的字推走造成的位移算進去。
那量到的是版面,不是字形。

`block-02-mono` 的做法:每列固定高度 + `overflow:hidden`,
讓任何一列的差異都只代表那一列自己的字形變了。
對帳站上的差異時,也要分清楚「這個像素差是字形差,還是被前面的中文推走的」。

### 6. 這套工具自己不能兩隻同時跑

**症狀:截圖一半是你的、一半是別人的,而兩邊都沒有錯誤訊息。**

`shoot.sh` 碰的每一樣東西都是共用的:

```
PORT=8999                                  單一硬編碼的埠
rm -rf "$H/.work" && mkdir -p "$H/.work"   單一共用目錄,而且第一件事就是 rm -rf 它
build.sh → tokyo-trip/retro-modern.built.css   直接寫進共用工作樹裡被追蹤的檔
```

後跑的那隻會 `rm -rf` 掉前一隻**正在用的**工作目錄。前一隻於是對著半個目錄、
或別人的產出拍照。**這正是這整套工具存在的理由(無聲失敗),卻長在工具自己身上。**

已修:開頭用 `mkdir`(原子的)搶一把 `.lock`,搶不到就印出持有者並 `exit 2`。
`probe.sh` 共用同一把。

> **「持有 harness」是一把鎖,不只是一個習慣。** 它比「凍結 design-system」更基本 ——
> 凍結管的是相依,這條管的是工具本身。這個 repo 同時有好幾個 session 在動,
> 開跑之前先確認沒有別人在截。

#### 這個坑修了兩次,而第一次寫下的結論是錯的

```sh
trap 'rm -rf "$LOCK"; [ -n "${SRV:-}" ] && kill "$SRV" 2>/dev/null; true' EXIT INT TERM
```

**`set -e` 在 trap 裡面照樣有效**,而 `[ ] && kill` 是一個複合句 —— `kill` 失敗時整句失敗,
trap **在那裡中止**,末尾那個 `; true` 根本沒跑到。
`shoot.sh` 正常結束前會先 kill 一次 SRV,所以 trap 跑到時那個 pid **一定**是死的 ——
也就是說**它每一次成功都回傳 1**。沒人發現,是因為兩支的輸出一路都被 `| tail` 接走。

後果:`./shoot.sh a && ./shoot.sh b` 會在第一支之後停住,而訊息會說截圖失敗 —— 它明明成功了。
已改成 `if ... then kill ... || true; fi`,兩支都驗過退出碼是 0。

> **這一段的重點不是 bug,是那個「已修復」。**
>
> `block-03` 已經踩過這個坑一次 —— 在同一個檔案、距離三行的 PROVENANCE 區塊 ——
> 並且把結論寫成註解留了下來:「注意 `&&` 不能是這個區塊的最後一句」。
> 那一輪之後,這個坑在紀錄上是**修好的**。
>
> **兩件事都錯了:**
>
> 1. **範圍錯**:只修了踩到的那一句,**沒有回頭在同一個檔案裡 grep 一次同樣的形狀**。
>    三行外的 trap 裡就有一個,兩支腳本都有。
> 2. **結論錯**:那一輪留下的解法是「末尾補一個 `; true`」。
>    **實測擋不住** —— `set -e` 是在 `kill` 失敗的那一刻中止 trap 的,`true` 根本沒跑到。
>    真正有效的是把 `&&` 拆成 `if ... fi`。
>
> **一個錯的「已修復」比沒修更糟:它會讓下一個人不再看那裡。**
> 這個坑之所以活了一整輪,不是因為沒人知道它,是因為紀錄說它死了。
>
> **而它的訊號一直都在。** 退出碼從第一天起就是 1,只是兩支腳本的輸出
> 一路都被 `| tail` 之類的東西接走 —— **訊號活著,只是沒有人站在它的頻道上。**
> (這份文件裡至少有三個同形的故事:被當成噪音的 modified 產出檔、
> 永遠都在響所以沒人讀的落後警告、以及這一個。**檢查有沒有人在看,跟檢查有沒有輸出,是兩件事。**)

**附帶一條,很少見但會浪費你半小時:腳本執行中不要改腳本自己。**
sh 是按**位元組位移**邊讀邊執行的。我在第一隻還在跑的時候編輯了 `shoot.sh`,
位移一偏,那一隻就在半行的地方報 `syntax error near unexpected token`。
**檔案本身沒壞**,是跑到一半的那個行程被我改掉了 —— 看起來卻像是你剛剛把腳本改壞了。

## 最貴的一個教訓

**差異式檢查對「兩邊都是空的」完全無感。**

工具壞掉的那次,每一頁都一致地空白,九張比對全綠。還跑了「同一狀態連跑兩次完全相同」
來證明工具是決定性的 —— **它確實是決定性的,只是決定性地壞掉。**

> **決定性是必要條件,不是充分條件。**

而且因為這個,假資料裡三筆花費**從來沒渲染出來過**,花費那頁在前幾輪一直是空白的。
接線那輪的結論沒有錯(其他八張是實的),但覆蓋率比當時報的低。
**結論對和驗證夠強是兩件事。**

### 補救:正向斷言

每張圖另外附一條「這一頁至少要有這些東西」,絕對式的,不依賴任何基準。
斷言寫在 `shoot.sh` 最底下每個 `shot` 呼叫的最後一個參數。

| 畫面 | 斷言 | 健康時實測 |
| --- | --- | --- |
| 01 / 02 行程 | `.stop:3+` | 3 |
| 03 花費 | `.exp:3+,.rm-chip:3+,.catrow:2+` | 3 / 3 / 2 |
| 04 分帳 | `.fp:5+` | 5 |
| 05 許願 | `.wish:3+` | 3 |
| 06 地圖(當日) | `.map .pin:4+` | 5 |
| 07 地圖(許願) | `.map .pin:6+` | 9 |
| 08 加行程 | `#stop-form:not([hidden]) input:3+,.stop:3+` | 3 / 3 |
| 09 編輯 | `#edit-overlay:not([hidden]) #edit-form input:3+,.stop:3+` | 5 / 3 |

**這條防線本身驗過了**,兩個方向都看過:
健康時九張全 `✓`,把第 2 條那個壞掉的 Date shim 放回去之後九張全 `✗`。

> **03 的斷言含 `.rm-chip:3+`,所以第一塊如果被回退,03 會印 `✗`。**
> 那是刻意的 —— 轉換開始之後要同時防「該變的沒變」,而這條順便把它綁進來了。
> 看到 03 `✗` 先確認第一塊還在,不要先當成工具壞了。

#### 收緊過的四條,以及為什麼

負向對照的第一次結果是**九張裡有三張漏接** —— app 已經死到標題列印 `NaN 天`、
行程花費許願全空,07 / 08 / 09 還是印 `✓`。原因各不相同:

- **08**:`#stop-form input` 量的是**靜態 markup**。那三個 input 本來就寫在 HTML 裡,
  app 開不開機都在;而且 `#stop-form` 預設帶 `hidden`,表單根本沒打開也算數
- **09**:同上,而且更嚴重 —— 09 的動作是 `d.querySelector('[data-edit-stop]').click()`。
  app 死掉時根本沒有 `[data-edit-stop]`,這行丟例外、被 `try/catch` 吃掉、
  **對話框從頭到尾沒開過,而斷言還是過。那條斷言從來沒有驗到它名義上要驗的東西。**
- **07**:門檻 2 太低。app 死掉時航班那兩個寫死的成田機場點照樣畫得出來
  (走 `OUTSIDE` 硬表,不經過 app 的資料層),剛好湊到 2

教訓:**斷言要挑「只有 app 真的跑起來才會存在」的東西。** 靜態 markup 不算。
量「容器開了沒」(`:not([hidden])`)比量「裡面有幾個 input」誠實。

#### 解析器自己的坑

斷言字串原本是 `spec.split(":")` 取 `p[1]` 當門檻。選擇器裡只要出現 `:not()`
這種偽類,門檻就會被切成字串,`parseInt` 得 `NaN`,而 **`n < NaN` 永遠是 false** ——
斷言不報錯,只是從此不再檢查任何東西。上面要加的 `:not([hidden])` 剛好會踩到。

已改成從**最後一個**冒號切,而且門檻讀不出數字時明確報錯。
**這個專案的招牌失敗模式,那次是埋在檢查器自己的字串解析裡。**

#### 涵蓋範圍到哪裡

負向對照只做了「app 完全沒開機」這一種壞法。**沒有**測「只有某一塊 CSS 沒生效」
那種局部壞法 —— 正向斷言本來也不是為那個設計的(那是差異式檢查的工作)。
全部是 headless Chrome,沒跑過真實裝置或真實 Safari。

> **而「沒跑過真實 iOS」這一句在第四塊變成了一個具體的欠款。**
> 那一塊整個決定(保留 `:521` 的 16px)就是為了防 iOS Safari 對焦放大,
> **而這套工具在定義上驗不到它** —— 能證明的只有「觸發條件不成立」(font-size 是 16px),
> 不是「行為沒發生」。見最上面「第四塊留下一件要真人做的事」。
> **有人要拿 iPhone 點一下。**

#### 那九張截到了哪些狀態,又漏了哪些

**這一節是 `block-02-mono` 那一輪撞出來的。** 在那之前沒有人寫下來過,
而它造成的症狀非常像「該變的沒變」:

| 狀態 | 有沒有被截到 |
| --- | --- |
| 行程 / 花費 / 分帳三個分頁 | ✅ 01–04 |
| 許願清單(`#wishbox` 展開) | ✅ 05 |
| 地圖(當日 / 許願) | ✅ 06 / 07 |
| 新增行程表單、編輯對話框 | ✅ 08 / 09 |
| **航班板 `<details class="board">`,手機寬度** | ❌ **從來沒有** |
| 手機寬度 + 任何 `<details>` 展開 | ❌ 沒有 |
| **記一筆花費 `#exp-form`、改一筆花費 `#exp-edit-overlay`** | ❌ **從來沒有** —— 裡面有 16 個欄位 + `.who` 那一整組,第三塊和第四塊都因此驗不了 |
| **任何對焦以外的互動狀態**(hover / 展開 / 錯誤訊息) | ❌ 沒有。08 的第一個欄位剛好是對焦的,那是 app 自己 focus 的,不是刻意截的 |
| 深色 / 高對比 / 縮放設定 | ❌ 沒有 |
| Google Fonts 載入失敗(斷網)的樣子 | ❌ 沒有 |

**`<details class="board">` 預設是關的。** 它在 02 / 07 兩張桌機圖裡是展開的,
在三張 390px 手機圖裡從來沒有。裡面有 **4 個吃 `--font-mono` 的中文元素**。

> **最容易被誤判的地方:關著的 `<details>` 裡的元素照樣有 computed style。**
> 你在 DOM 上盤點時它會被算進去、進了「預期會變」清單,然後在截圖裡永遠不出現 ——
> **看起來跟「該變的沒變」一模一樣,而那是驗收規則第 4 點要抓的東西。**
>
> 盤點完要再問一句:**這個元素在哪一張截圖裡真的畫得出來?**
> 答不出來的,就不要寫進那一輪的預期清單,改寫進「沒驗到的事」。

## 驗收規則

**兩套規則,看那一輪該不該改變外觀。**

### 不該改變外觀的輪(包 layer、接線)

零差異。**任何非零一律當成問題查,不准先歸因到任何已知效應。**

「帶著預期去驗收」會讓第一反應變成歸因而不是追查,那就毀掉驗收的意義。

### 該改變外觀的輪(每一塊轉換)

零差異反而代表沒生效。所以:

1. **動手前**先寫下預期會產生哪些視覺變化,逐項寫進 `block-NN-*.md`
2. 比對後,把實際差異逐一對到清單上
3. **清單外的差異是問題**,不管看起來多合理
4. **清單上有、但實際沒出現的也是問題** —— 那代表你以為會生效的東西沒生效
5. **「我驗不到這個」也要查證過再寫。** 把涵蓋率**報低**看起來保守無害,
   實際上是放棄一個其實有效的驗證管道

第 4 點容易被忽略。前面幾輪一直在防「不該變的變了」,轉換開始之後要同時防「該變的沒變」,
而後者在 CSS 裡一樣不報錯。

第 5 點是 `block-04` 那一輪自己撞到的:事前登記寫了「`:focus-visible` 這一輪驗不到
(截圖不對焦)」,**而 08 的第一個欄位在截圖裡就是對焦的** —— app 自己 focus 了它。
那一輪剛好在同一個地方發現一個真的回歸(對焦時圓角 8px→4px),
**如果當時信了自己那句「驗不到」,那張圖就不會被拿來看。**

> **登記不準有兩個方向,而低估的那個方向感覺起來像謙虛。**
> 「我驗不到」跟「我預期它會變」一樣是一個斷言,一樣要有根據 ——
> 最便宜的根據就是**把那張圖切出來看一眼**。

已知且無法消除的差異,要在**該輪開始之前**登記。事前登記和事後歸因看起來像同一件事,
但前者可以被檢驗、後者不能。

`block-01-chip.md` 是完整的範本:為什麼挑這塊、預測表、實際結果、偏離的解釋。

## 怎麼挑一塊

- **最小、最獨立、最容易單獨看到**
- **而且 design-system 裡要有語意對得上的組件**
- **而且不要卡在別人還沒修的東西上**
- **而且要問一句:它出現在哪一張截圖裡?**

第二個判準比第一個重要。挑一塊在 design-system 裡沒有對應組件的,就會變成
「用 utility 手工拼出一個外觀」—— 那驗不到我們要驗的東西(組件在真實頁面上長得對不對)。

第三個曾經擋掉三塊:`rm-chip`、`rm-overline`、`rm-day-pin` 都吃 `--font-mono`,
而當時 mono 沒有 CJK fallback。**那個阻礙已經解除**(`block-02-mono` 補在
**tokyo-trip 自己的 `:root`** 上,不是 design-system 那一份)。

**第四個是 `block-03-label` 那一輪學到的。** 那一塊改了 32 個標籤,
**九張截圖只看得到 9 個**,其餘 23 個躲在沒有被打開過的表單和對話框裡。
不是不能做,但要**事前就知道自己驗得到多少**,並且在該輪的
「沒有驗到的事」裡寫清楚 —— 而不是做完才發現覆蓋率只有三成。
挑一塊之前,先對著九張截圖問:**這一塊會出現在哪幾張?**

可用的組件(`design-system/retro-modern.css` 的 `@layer components`):

```
rm-base  rm-btn(--action/--cta/--ghost/--lg/--secondary/--sm/--steel)
rm-card(--arch/--expressive/--raised/--surface)  rm-chip(--accent/--solid)
rm-day-pin  rm-divider(--dashed)  rm-input  rm-label  rm-overline
rm-row  rm-stack  rm-toast
```

### 第五塊:沒有現成的推薦,而最值得做的一塊是「先補一張截圖」

第四塊做完之後,剩下語意對得上的組件都卡在同一件事上:**它們出現的畫面沒有被截到。**

`shoot.sh` 的九張裡,**沒有任何一張打開過 `#exp-form`(記一筆花費)或
`#exp-edit-overlay`(改一筆花費)**,而那兩個容器裡有:

- 16 個欄位(`ef-*` 8 個、`xe-*` 8 個)—— 第四塊只有 computed 值,沒有畫面
- 10 個 `.who` 核取方塊 + 10 個成員膠囊 —— **第三塊和第四塊各凍了一次的舊樣子**
- `input[type=number]` 的等寬金額欄位 —— 第四塊確認它活著,但**沒有任何一張圖看過它**

所以:**加一張 `10-exp-form` 截圖本身就可以當成一塊。** 成本很低 ——
`probes/inputs.js` 已經用真實點擊把那兩個容器打開了,同一串動作搬進 `shoot.sh` 即可:

```sh
shot 10-exp-form 390 1400 "d.getElementById('tab-cost').click(); d.getElementById('add-exp-btn').click();" \
     "#exp-form:not([hidden]) .rm-input:5+,.who label:4+"
```

補完之後,`.who` 那一整組(膠囊 + 核取方塊)才**驗得了**,那就是很自然的第六塊。

> **它凍了兩輪了。** 第三塊凍了 `color` / `letter-spacing`,
> 第四塊凍了 `width` / `background` / `font-size` / `line-height` ——
> 其中 `width:100%` 把 13px 的原生核取方塊撐成 28px,**看起來就是個意外**。
> 兩輪都選擇不碰,理由每次都一樣:**沒有截圖就驗不了。**
> 這不是膽小,是規則第 4 點(「該變的沒變也是問題」)在沒有畫面的地方根本執行不了。

### 第四塊實際做了什麼(已完成,細節見 `block-04-input.md`)

Lulu 的決定是**保留 `:521` 的手機 16px 覆寫、刪掉 `:419` 的桌機基底規則**。
下面幾件事是那一輪量出來的,對之後的每一塊都還適用:

- **`.fld input`(0,1,1)高過 `.rm-input`(0,1,0)**,跟載入順序無關。
  同理 `:423` 的 time/date、`:430` 的 number 覆寫(都是 0,2,1)都活了下來,量過。
- **`padding` 在九張截圖裡一個像素都沒變。** `ADOPTION.md` 舊版寫「欄位會明顯變高」,
  那是把桌機的值當成了截圖的值 —— **08 / 09 都是 390px**,`:521` 贏。
  這一塊實際的高度變化只有框線 1px→2px 帶來的 **+2px**。
  > **教訓:寫「這一塊會怎麼變」之前,先確認那一張截圖是幾 px 寬。**
  > `probe.sh` 現在有 `WIDTH=`,不要再只量 1100。
- **刪一條規則,會讓一堆一直被它遮住的宣告浮出來。** 第三塊是 `.fld label` 漏給 `.who label`,
  第四塊有兩處:`.fld input` 也選到 `.who` 的核取方塊,
  以及 `:53` 的全域 `:focus-visible{border-radius:4px}` ——
  以前 `.fld input` 蓋得過它,換成同特異度的 `.rm-input` 之後,**對焦會把圓角從 8px 變 4px**。
  兩處都在那一輪補回去了。
  > **找這種東西的方法是量,不是讀。** `:focus-visible` 那條是探針的離群值報出來的,
  > 讀 CSS 的時候完全沒想到。

**排除掉的**:`.btn` → `rm-btn`(九張全會變、七個變體要對應,太大);
`.day` → `rm-day-pin`(語意不對 —— `rm-day-pin` 是 28×28 的圓形號碼牌,`.day` 是整張日卡。
真正對得上的是時間軸的數字圈和地圖 pin,但那會同時動到四張,而且 pin 尺寸一變
地圖標籤的碰撞讓位就整個重算);`.cloudbar`(最接近的 `rm-toast` 是浮在角落的提示,語意不對)。

## 約束

### 不要用 opacity modifier

`bg-paper/50`、`text-ink/70` 這一類。它們編出來是 `color-mix`,**在 iOS 16.3 以下
整條宣告無效** —— 不報錯,背景就是不上色。

Lulu 對 iOS 版本的答覆是「以最新版為主」,那是**假設不是事實**(她沒有去問那四個人)。
避開這類 utility 就避開了這個假設的主要暴露面。需要半透明就用明確色值或自己的 `:root` 變數。

### `<link>` 必須在 `<style>` 之前

不是保險,是**必要條件**。兩邊的組件都在 `components` 層,同層之內比特異度再比原始碼順序,
**後載入的贏**。design-system 先載入,`.card` 才蓋得過 `.rm-card`。

反過來的話它的組件會開始無聲蓋掉這邊寫好的東西。

### `:root` 留在 `@layer components` 外面

自訂屬性一旦進了層,任何無層級的 `:root` 都蓋得過它。留在外面就永遠是這邊說了算 ——
那也是之後想覆寫 design-system 某個 token 時唯一有效的位置。

> **這條同時是保護傘和阻礙,而後半段害過一次。**
> 「永遠是這邊說了算」的另一面是:**design-system 對同一個 token 的修正永遠到不了這裡。**
> 實際發生過 —— `--font-mono` 缺 CJK 後援,有人去修了 design-system 那一份,
> 重編之後九張零差異,因為 tokyo-trip 的 `:root` 擋著,那個修正從來沒到達任何元素。
>
> **要查一個 token 現在是誰說了算,不要讀 CSS 猜,直接在真實 DOM 上問:**
>
> ```js
> getComputedStyle(document.documentElement).getPropertyValue('--font-mono')
> ```
>
> 兩邊的 token **同名而且值長得很像**,分辨的方法是**只看第一個字體名**。
> 完整的辨識表和那次繞路的經過,寫在
> `block-01-chip.md` 的「怎麼分辨這個 computed 值是誰的 stack」。

### 改 markup 之後一定要重編

Tailwind 是 content-driven,掃 `tokyo-trip/` 決定編出哪些 utility。
用了新 class 沒重編 = 那個 class 不存在 = 樣式安靜消失。

**已經做進 `shoot.sh` 了**,截圖前自動重編,不是人要記得的事。

## 已登記的盲區

產出的 `utilities` 層有 8 個 class:

```
block  ease-out  filter  hidden  inline  resize  sticky  transform
```

**沒有一個是 markup 在用的。** 掃描器從 CSS 屬性值、JS 字串、**甚至中文註解**裡撿出來的:
`padding-block`、`position:sticky`、`cursor:col-resize`、`backdrop-filter`、
還有註解裡寫的「用 clip 不用 hidden」。

**後果:這 8 個名字不受「忘了重編」偵測保護。** 哪天想拿其中一個當 utility 用
(例如 `class="hidden"`),它早就在產出裡了,忘記重編也不會被抓到。

不修:為了 8 個常見字去調掃描規則,成本高於收益。詳見 `tokyo-trip/app.css` 的註解。

### 它曾經變成 11 個,而原因是這份文件自己

`9262c9a`(把這份文件寫出來的那個 commit)之後,重編一次會多出三個:

```
backdrop-filter   bg-paper\/50   text-ink\/70
```

因為當時這份文件住在 `tokyo-trip/`,而它的「不要用 opacity modifier」那段
字面寫著 `bg-paper/50` 和 `text-ink/70`、「已登記的盲區」那段字面寫著 `backdrop-filter`。
**掃描器把警告文字本身撿去編成了 utility。**

連帶的第二個症狀:`tokyo-trip/retro-modern.built.css` 是在這份文件進 repo **之前**編的,
所以從那時起 git 裡的產出就跟它的原始碼對不上了 —— **任何人跑一次 `shoot.sh`
都會讓它變成 modified**,而那看起來像是自己不小心改到的。

把文件搬到 `adopt-harness/` 之後重編,產出回到 8 個 class,而且跟 `9262c9a` 裡那份
**逐位元組相同**。這個故事比結論有價值:
**掃描範圍的邊界不只約束程式碼,也約束你寫在那個資料夾裡的每一個字。**

### 而上面那句「跑一次就會變 modified」害過一次,要更正

那個症狀當時是真的(產出跟原始碼對不上),搬走文件之後**已經不成立**了。
但那句話留在這裡,而且它做的事比過期更糟:

`design-system/` 一髒,`tokyo-trip/retro-modern.built.css` 就會跟著變。
那個檔在舊版出處紀錄的範圍內 —— 換句話說,**「凍結被打破了」這件事一直有一個訊號,
而這份文件親手把那個訊號標成了噪音。**

> **那比「紀錄範圍太窄」嚴重得多。範圍窄是遺漏;教人忽略,是主動拆掉一道還在運作的防線。**

現在的出處紀錄會單獨列出相依的狀態,不必再靠產出檔去推。
但這件事值得記住,因為它會再發生:**在文件裡寫「這個訊號可以忽略」之前,
先確認它真的只有噪音的意思。**

## 多 session 協調規則

這個 repo 同時有別的 session 在動(`design-system/` 由另一隻負責),共用**同一個工作樹**。

- **提交前先問協調者**(`playground-8b`)。編輯可以並行,提交不行
- **逐檔 `git add`,不要用 `-A` 或 `.`** —— 會把別人手上的檔案掃進去。
  我實際遇過一次:協調者放行時說工作樹只有我的檔,我 add 之前重讀,
  發現另一隻已經落盤了兩個檔。**放行不等於工作樹狀態的保證,自己重讀。**
- **`DECISIONS.md` 一次只有一隻能寫**,要先拿鎖
- **一輪轉換進行中,design-system 凍結**。相依一動,差異就無法歸因。
  開始一塊之前跟協調者說,做完回報才解凍。
  **現在出處紀錄會單獨記相依的狀態**,凍結有沒有被打破,事後查得到
- **同一時間只有一隻能持有 harness**(`shoot.sh` / `probe.sh`)。
  它們共用 `.work/`、共用埠、共用產出檔 —— 腳本自己有鎖會擋,但排隊還是要先講。
  見「工具的陷阱 6」
- **開工前先問協調者「現在有誰在動哪裡」**。實際發生過:兩隻 session 被指派了
  **同一塊**,差四分鐘,兩邊都要改 `tokyo-trip/index.html` 和同一份 `block-03-label.md`。
  擋下來的不是工具,是**動手之前先回報**這個習慣

### 一塊一個人(Lulu 在第三塊之後定的)

**每完成一塊、提交之後,那個 worker 更新這份文件,然後換下一個人接。
不等 session 的上下文用完,在自然的邊界換手。**

理由:上一隻(Tokyo trip)的上下文用完時卡在半途,**而且不是它自己發現的**,
是 Lulu 看到才講的。

> **session 看不太到自己還剩多少**,所以「滿了就換」沒有可靠的觸發器 ——
> 那正是這個專案一路在拆的那種「靠人注意」的機制。
> 換成**事件觸發**(一塊做完)就不需要偵測狀態了。

附帶的好處:**這份文件每一塊都會被真的用一次。** 它的缺口就是這樣被挖出來的 ——
`block-02-mono` 那一輪挖出「量字體的四個陷阱」沒有寫下來,
`block-03-label` 那一輪挖出出處紀錄看不到相依、harness 不是併發安全的。
**沒有換手就沒有這些。**

接手的人要做的第一件事,見最上面「現在做到哪」的三行指令 —— 先問線上是什麼,
再讀這份文件,**然後自己重截一次基準用 `cmp` 驗過**再開工。
