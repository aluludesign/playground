# `via` 在寫進快取那一刻掉了 —— 人工表那句話只有一半的路看得到

**接在 `geocode-outside-and-notice.md` 後面。** 那一輪把人工表接回了「標題」那條路,
報告 114 條斷言全綠、十一張截圖零差異,推上線。Lulu 在真機上用了之後回報:

> 桃園那一列按一次「再查一次」只有說沒標上去,根本沒有看到新提示不在日本境內。
> 沒填地點的對了。

兩件事裡對了一件。**而沒對的那一件,探針把它斷言成了正確行為。**

---

## 根因:一個標記,兩個寫入端,都沒帶它

`paintFix()` 判斷「這顆座標來自人工確認過的表」靠的是 `at.via`(`index.html:1758`),
而 `via` 只掛在 `outsidePin()` 的**回傳值**上。一寫進 `pins[place]` 就掉:

| 寫入端 | 舊的樣子 |
| --- | --- |
| `pinFor()` 表命中 | `pins[place] = { la, lo }` |
| `regeoItem()` 地點欄命中(`kp`) | `pins[item.place] = { la: kp.la, lo: kp.lo }` |

於是人工表那句話**只有在 `pins[place]` 是 falsy、`pinOf` 掉到標題那一步的時候**才講得出來。

| 關鍵字寫在哪 | 走哪條路 | 講得出人工表嗎 |
| --- | --- | --- |
| 標題(`桃園機場 第一航廈 報到`,地點欄是航班備註) | `outsidePin(item.title)`,`via` 還在 | ✅ |
| **地點欄**(`TPE 桃園 T1`、`NRT 成田 T1`、箱根…) | `pins[place]`,`via` 掉了 | ❌ **「沒標上去」** |

Lulu 按的是後面那一種。**而且這不只影響一句話** —— `:1766` 的
`el("map-fix-go").hidden = !fixItem.place || manual` 也讀同一個 `manual`,
所以「再查一次」在一顆人工驗過的座標上**該收起來卻沒收**,跟上一輪的決定正好相反。

### 影響範圍比桃園大

箱根、成田、富士、迪士尼、橫濱 —— **所有把關鍵字填在地點欄的列**,
人工表那句話從來沒有出現過。桃園只是第一個被人撞到的,因為它同時還不在日本境內,
所以那一句話的缺席特別明顯(「沒標上去」聽起來像壞掉)。

## 探針把 bug 寫成了基準

`probes/geofix.js` 上一輪是 114 條全綠,其中兩條是這樣寫的:

```js
ok("地點欄本身命中表的那幾筆沒有被弄壞(成田照樣標得出來)",
  await until(function () { return /不在這裡/.test(barText()); }), barText());
ok("成田那一筆的「再查一次」照樣畫得出來(它有 pin,使用者說不對還是能按)",
  q("#map-fix-go").hidden === false, null);
```

**那兩條斷言的內容就是 bug 的樣子。** 寫的時候標題還寫著「它們從頭到尾沒壞過,
這裡順便確認這一輪沒有把它們弄壞」—— 也就是說,寫的人以為自己在做迴歸保護,
實際上是把當下的行為原樣抄成了期望值。

> **這個 repo 已經有一句話講這件事:「問錯的問題會得到一個乾淨的、錯的綠燈。」**
> 這一輪的版本更窄也更常見:**「順便確認沒弄壞」的斷言,如果期望值是從當下行為抄來的,
> 它保護的就是當下的行為,包括當下的 bug。**
> 上一輪那 114 條裡,`kp` 命中那條路一條真正的斷言都沒有 —— 11 段測的全是標題那條路。

## 改了什麼

### 1. 兩個寫入端都帶上 `via`

`pinFor()` 寫 `{ la, lo, via: place }`,`regeoItem()` 寫 `{ la, lo, via: kp.via }`。
`via` 存的是**被比對到的那個字串**,所以介面印得出來是哪幾個字命中的。

### 2. 開場跟人工表對一次帳

光補寫入端修不到已經在五個人瀏覽器裡的舊資料 —— `pinFor()` 開頭那句
`if (place in pins) return pins[place]` 會直接回頭。所以載入時掃一次快取:
凡是這張表答得出來的 key,一律換成表的值並補上 `via`。

- **不換快取 key。** 換 key(`57473b5` 那次的做法)會把大家查好的、跟這張表無關的
  座標一起丟掉,然後每一顆重查一次、每次排隊 1.1 秒。這裡只動表答得出來的那幾個 key。
- **對完帳之後,快取裡的值就等於「這台裝置第一次載入會算出來的值」。**
  也就是說 **N7 那筆債還掉了:沒有人需要為了拿到正確座標去按「再查一次」。**
  上一輪把「要 Lulu 自己再按一次」寫成待辦,而那是程式修得掉的事。

### 代價(知道而且接受)

- 有人曾經對一個「表答得出來的地點」按過「再查一次」拿到比較準的線上座標
  (例如 `箱根湯本站` → 表只給箱根的概略中心),**對帳會把它換回表的值**。
  但上一輪的 `regeoItem` 已經讓那種座標**再也查不回來**了(表命中就直接回,不打 API),
  所以這不是新的單向門,只是把已經做過的決定補套用到舊資料上。
- 對帳會清掉那幾筆上的 `ok`(使用者按過「對」)。表的值本來就不帶 `ap`,
  `paintFix` 的 `asking` 永遠是 false,所以那個確認沒有作用可以失去。

## 順手查到、**不是這一輪造成**的一件事

`geocode-outside-and-notice.md` 的「決定 2」把人工表誤傷的範圍登記成
「地點欄是空的或查不出東西,而標題含表裡的關鍵字」。**那個範圍寫窄了。**

`pinFor()` 的表比對排在線上查詢**之前**(`index.html:1886`),所以地點欄填
`富士電視台` 的那一筆,在任何一台冷快取的裝置上都會直接拿到河口湖,差 100 公里 ——
跟標題那條路無關,而且一直都是這樣。

**沒有在這一輪動它**,理由:那張表同時服務天氣(`resolvePlace`),改 key 或改比對
方式是三個消費者一起變,要 Lulu 先拍板。登記在這裡。

## 驗收

### 探針:126 條,而且證明得出它測得到東西

`probes/geofix.js` 114 → **126 條**,全綠。新增的分成三組:

| 組 | 測什麼 |
| --- | --- |
| 1b | 舊快取對帳:錯座標被換掉、`via` 補上、寫回 localStorage、**表答不出來的 key 一個字沒動**、`null` 沒被當成要修的 |
| 11b | 地點欄命中表 → 講得出「在人工確認過的表裡」「不在日本境內」、印的是地點欄那幾個字、「再查一次」收起來 |
| 11b(成田) | 同一條路的**另一半**:在日本境內 → 講「用的是人工確認過的座標」、按鈕也收起來、pin 還在 |

**拿去跑修改前的程式(`SRC=/tmp/wt-prefix/tokyo-trip`),10 條掛。**
沒有這一步的話,新斷言有沒有在測東西是不知道的 —— 上一輪那兩條綠的錯斷言就是這樣來的。

`fixture.py` 多灌一筆 `"TPE 桃園 T1": {la:35.6812, lo:139.7671}` ——
那是東京車站的座標,離桃園 2000 公里,而且沒有 `via`:**Lulu 那台裝置的狀態**。
沒有它,「舊資料自己修好」就沒有人測。

### 我寫的第一版斷言是假綠燈,探針第一次跑就抓到

第一版等的是 `/人工確認過的表裡/`,而**上一列(桃園機場報到)講的就是那句話** ——
`until()` 在這一列重畫之前就通過了,後面兩條斷言量的是上一列的字。

> **等待條件必須是「這一列才有的字」。** 畫面上留著的舊字會讓
> 「等到了」跟「換好了」看起來一模一樣。這是工具陷阱 10(斷言和截圖不是同一趟)
> 在同一支探針內部的版本:**兩次斷言之間,畫面也不是同一個時刻。**

### 截圖:十一張,`01`–`10` 與 `shots/gx-after` 逐位元組相同

`11` 落在已登記的雙穩態(8px / 6 個單列群 / `x=86`),重截跳回去。
這一輪不該改變任何外觀 —— `#map-fix` 那一條預設 `hidden`,
十一張裡沒有任何一張是「在地圖裡點了某一列之後」的狀態。

### 走了一段冤枉路,而原因是這份文件的索引

**「現在做到哪」那節寫著「用 `shots/expform`(唯一有 10 / 11 的一組)」,
而「基準」那節寫的是 `shots/gx-after`。** 我照索引拿了 `expform`,
於是 06 差 2.3%、07 差 127px,花了四趟截圖才分清楚那是基準過期、不是我改壞。

06 對 `expform` 的那 2.3% 是**上一輪「規則一」的正當結果**(沒填地點的 teamLab
不再標上去),`expform` 是那之前的組。

> **這是同一份文件第三次被自己的過期索引咬。** 前兩次是「線上現在是什麼」,
> 解法是「不留答案,只留產生答案的方法」。這一次是基準名 ——
> 同樣一個每輪都會變的事實,被寫進了兩個地方,只更新了其中一個。

### 07 差的那 127 px 不是抖動,是修好的證據(我一開始判斷錯了)

四趟截圖裡,07 出現過兩個值,而差異是標題那行的**數字**:

```
舊碼 + 這份新 fixture   大家想去的地方  願望 1／3 · 行程 8
修好之後              大家想去的地方  願望 1／3 · 行程 6   ← 與 shots/gx-after 相同
```

**我第一個判斷是「07 是非決定性的」,那是錯的。** 同一個組合連跑三次都給同一個雜湊
(`cc553fca`),它是決定性的 —— 是**我少跑了那一趟的重複**就先下結論。

真正的因果:快取裡那個假座標(東京車站)**在日本境內**,所以修好之前,
`TPE 桃園 T1` 那兩列(`MM626 起飛`、`抵達桃園機場`)進得了可繪集合,`行程` 就多 2。
對帳把它換成桃園(`25.080`,`inJapan()` 之外)之後,兩列退出,回到 6。

數出來的(`WIDTH=1100`,同一支一次性探針跑兩棵樹):

| | 標題 | pin 數 | 差別 |
| --- | --- | --- | --- |
| 修改前 | `願望 1／3 · 行程 8` | 9 | 多 `1MM626 起飛` 和 `6抵達桃園機場`,都在 `@2323,-2924` |
| 修改後 | `願望 1／3 · 行程 6` | 7 | 兩列都退出;`快取TPE` = `{la:25.08, lo:121.234, via:"TPE 桃園 T1"}` |

> **那兩顆的座標是 `@2323,-2924` —— 在畫面外。**
> 所以地圖區**一個像素都沒有變**,整張圖的差異全部落在標題那 17 列。
> 這正是工具陷阱 11(「量到的位置可能根本不在畫面上」)的另一面:
> **畫面沒變不代表狀態沒變**,而這次唯一把狀態洩漏到畫面上的,是一個數字。
> 如果 `map-n` 不印那個數字,這顆幽靈 pin 在十一張截圖裡是完全隱形的。

### 那顆幽靈 pin 本來會被畫在東京車站

修好之前,五個人裡**任何一個按過「再查一次」而拿到錯座標的人**,
他的許願地圖上就會有一顆標著「MM626 起飛」的 pin 插在東京車站附近 ——
而畫面上沒有任何東西說那是錯的。這一輪的對帳把它清掉,不需要任何人動手。

(這次它沒出現在截圖裡,只是因為 fixture 那張圖的縮放剛好把它推到畫面外。
**不要把「這次沒看到」讀成「它不會出現」**。)
