# 地名這件事的另外兩段:不該查的不查、查了不確定的由人定

**接在 `geocode-retry.md` 後面。** 那一輪做的是「查了但不確定」的退路
(使用者主動按「再查一次」,拿到 `APPROXIMATE` 就畫虛線圈)。
這一輪補兩件事,加起來才是完整的一條:

| 段 | 規則 | 這一輪 |
| --- | --- | --- |
| 一 | **不該查的不查** —— 沒填「地點」的,不拿標題去猜,一次 API 都不打 | 新增(Lulu) |
| 二 | **不查的要講** —— 送出的當下就說「它不會出現在地圖上,填了地點就會」 | 新增(Lulu) |
| 三 | **查了但不確定的由人定** —— 虛線圈 + 「這個位置對嗎? [對][再查一次]」 | 補上「對」那一半 |

> **不要拆散它們。** 第三段(上一輪)沒有第一段,等於「先讓機器猜錯,再請人來收拾」;
> 第一段沒有第二段,會製造一個新的無聲狀態(存進去了、地圖上沒有它,而使用者分不出
> 是「我沒填」「還在查」還是「壞了」);第二段沒有第三段,則是把所有不確定都丟給使用者。

**驗收不是純「零差異」那一套。** 第一段會讓兩顆本來就不該存在的 pin 消失,
所以 06 / 07 **預期會變**,其餘九張零差異 —— 混合式驗收,逐項登記在下面。

## 這一輪要改什麼(動手前寫的)

### 規則一:沒填「地點」就不查

`pinForItem()` 現在是「地點查不到就拿標題再試一次」。**標題是「做什麼」,地點欄才是「在哪」。**
拿「做什麼」當地名去查,就是那顆雲南 pin 的成因 —— 不是服務不準,是**問錯了問題**,
而換一家更貴的服務不會讓錯的問題變成對的。

| # | 預期 |
| --- | --- |
| R1 | `pinForItem()` 只查 `item.place`;沒填就回 `null`,**一次查詢都不發** |
| R2 | `pinOf()` 只讀 `pins[item.place]`,不再回頭讀標題那一筆快取 |
| R3 | `regeoItem()`(再查一次)的候選字串同樣只剩 `item.place` |
| R4 | 沒填地點的那一筆,連「再查一次」的按鈕都不畫 —— 按了也只會再問一次同一個錯問題 |
| R5 | 天氣那條路**不用改**:`loadStopWeather()` 本來就是 `if (!s.place) continue`。**這條規則有一半早就存在了,只是地圖那條沒跟上** |
| R6 | `OUTSIDE` 那張人工表**不受誤傷**,而且驗過:它比對的是傳進 `pinFor()` 的字串,而那個字串現在一律是 `place`。六個 `ANCHORS` 全部填了地點(`NRT 成田 T1`、`TPE 桃園 T1`、`都心 → NRT 約 60–90 分鐘`…),所以航班那幾個點照樣命中 |

#### 已經在快取裡、當初用標題查出來的錯座標怎麼辦

**不換 key。** `tokyo5-pin3` 留著,`pinOf()` 改成只讀地點那一筆就夠了 ——
錯的那些**正好就是標題那些 key**,而新規則從此不再讀它們。

- 換 key(`57473b5` / `14121ee` 的前例)是因為**一整批座標依規則錯掉**,
  而且對的和錯的長得一模一樣、分不出來。這次分得出來:
  **壞的那批的判準就是「這個 key 是某一筆的標題、而那一筆沒填地點」。**
- 這份快取是**以字串為 key**,不是以欄位為 key。同一個字串不管當初是從
  標題還是地點送出去的,查到的答案都一樣 —— 所以沒有「污染」,
  只有「該不該去讀它」。改讀取端比改儲存端乾淨。
- 換 key 的代價是把五個人瀏覽器裡**所有查好的座標**一起丟掉(包含全部正確的那些),
  換來的只是幾筆再也不會被讀到的死資料。不值得。

**留下的東西**:那幾筆死資料會一直躺在 localStorage 裡。
不去清:要清就得判斷「哪個 key 是標題」,而那要拿現在的資料去反推,
**而那個反推本身會有錯**(同一個字串可能同時是 A 的標題和 B 的地點)。
不讀它,它就只是佔幾百個位元組。

### 規則二:送出的當下就講

| # | 預期 |
| --- | --- |
| S1 | `checkPlace()` 遇到沒填地點 → `flash()` 說**會怎樣**和**怎麼辦**,而且**不打任何 API** |
| S2 | **不擋送出。** 沒填地點是合法的(「多喝水」「早點睡」那種願望本來就不需要上地圖)—— 這是告知不是驗證 |
| S3 | 許願表單送出也接上 `checkPlace()`。它**以前完全沒有回饋**,是這條規則最需要的地方(fixture 裡三個願望有兩個沒填地點) |
| S4 | 沿用 `flash()`,不長第三套提示機制 |
| S5 | 從清單點進地圖時,沒填地點的那一筆在「再查一次」那一條上也講同一件事(第二個時機,不是第二套機制) |

**為什麼選 flash 而不是在表單裡那一欄旁邊寫一行**(協調者給的另一個方向):

1. 表單裡加一行提示,**會改到 08 / 09 / 10 / 11 四張截圖**,而 `.fld` 那一整組
   正在被 design-system 逐塊轉換(第六塊 `.who` 就住在裡面)。
   在轉換進行中的版面上多塞一個元素,等於讓下一塊的「該變的變了」對帳多一個變數。
2. 那一行提示**每次都在**,而這個專案上一輪剛學到「常駐的提示會變成背景」。
   送出時講的是**當下這一筆**的事,它有具體對象。
3. 但表單那條方向本身是對的(在填的當下就知道那一欄的作用)。
   **登記成待辦,交給協調者排在 `.who` 那一塊之後** —— 不是否決,是排序。

### 規則三:虛線圈要變得回來(Lulu 自己設計的互動)

```
按「再查一次」,查到概略位置
   → 虛線圈
   → 那條列變成「這個位置對嗎?　[對]　[再查一次]」
按「對」      → 變實線,以後不再問
按「再查一次」 → 再查一次(就是現有的那顆按鈕)
```

| # | 預期 |

| C1 | `#map-fix` 多一顆「對」(`#map-fix-ok`),**只在那一筆的 pin 是概略而且還沒被確認過時出現** |
| C2 | 按「對」→ 那一筆快取多一個 `ok:1` → pin 的 `approx` class 消失 → **實線**,而且那一條回到「不在這裡?」的樣子,不再問 |
| C3 | **不做破壞性動作。**「不對」就是再按一次「再查一次」,沒有「刪掉這顆 pin」那種按鈕 |
| C4 | 「對」只寫 `localStorage`,**不打任何 API**(所以它不花錢,也不需要通行碼) |
| C5 | `ROOFTOP`(精確)的結果**不問**「這個位置對嗎」。理由見下面決定 2 |

## 實際結果

### 介面長什麼樣

地圖上方那一條(`#map-fix`,點過清單某一列之後才出現)現在有**四種**狀態:

```
「淺草寺」不在這裡?                     [ 再查一次 ]      ← 有 pin,精確或已經確認過
「淺草寺」這個位置對嗎?         [ 對 ]  [ 再查一次 ]      ← 只查到大概的範圍,還沒有人看過
「港灣未來」沒標上去                    [ 再查一次 ]      ← 有填地點,但查不到
「合羽橋道具街」沒填地點,不會出現在地圖上                  ← 沒填地點:兩顆按鈕都不畫
```

按「對」→ 那顆 pin 的虛線圈換成實線、標籤的「約 」留著、那一條退回第一種樣子,以後不再問。
**沒有「不對」那顆按鈕** ——「不對」就是再按一次「再查一次」。

送出的當下(加行程、許願,兩邊同一個 `checkPlace()`):

```
「多喝水」沒填地點,地圖上不會有它 —— 補上地點就會出現
```

**不擋送出。** 那一筆照樣存下去,只是它不會上地圖 —— 而他現在知道為什麼、也知道怎麼辦。

### 這一項我預測錯了:V5

我寫的是「剩下的 pin 座標不動;但標籤可能從 `below` / `hide` 回到正常位置」。
**座標確實沒動,但那句話描述的不是實際發生的事。**

真正發生的是**取景整個換了**:`drawMap()` 取景只看「主角」那組點(許願那層),
而 fixture 三個願望裡只有一個填了地點 —— 主角從兩個點變成一個點,
於是 `fit.length > 1` 不成立,縮放直接走「單點 z=14 並且以它為中心」那條路。

後果在 06 上最明顯:**DAY 3 的地圖現在以橫濱為中心**,
那一天的淺草寺和築地市場**還在 DOM 裡,但被推到畫面外** —— 圖上只看得到一顆 pin。

> **這是既有的取景規則遇到一組變小的「主角」,不是這次改壞的。**

### 新踩到的坑:斷言看的不是截圖那一刻

第一次跑完 `shoot.sh`,06 和 07 的正向斷言掛了(`.map .pin` 只有 3 / 4 個),
而**截圖裡實際是 3 / 7 顆**。查下去發現兩件事:

1. **斷言和截圖是兩趟不同的瀏覽器**(`shoot.sh` 本來就這樣設計)。
   截圖那趟拍的是 virtual-time budget 25s 跑完的終態;
   斷言那趟是在動作之後 **900ms** 量的。
2. 07 那三顆航班點要等 `樂桃 MM626 · 建議起飛前 2.5 小時` 那兩次 **Nominatim 真的回來**
   才畫得出來(探針量到約 1.2s)。900ms 的時候它們還沒到。

**以前這件事不會發作**,因為 900ms 時光是 fixture 快取裡那 6 顆就過了門檻 6;
規則一把其中兩顆拿掉之後只剩 4 顆,門檻才第一次咬到。

> **「斷言過了」和「截圖裡有」是兩個不同時刻的兩件事。**
> 這跟 `block-04` 那個「在 1100px 量 390px 的問題」是同一個形狀:
> **量到的東西跟你要回答的問題不在同一個座標上,而它不會報錯。**

處理方式(寫在 `shoot.sh` 的註解裡):
**門檻只認「不靠網路就一定在」的那幾顆** —— 06 是 3、07 是 4,不是截圖上的 3 / 7。
把門檻設成截圖上的數字,等於讓這條斷言變成網路的函數,那正是 `tokyo5-pin3` 那個坑的形狀。
同時**兩張各補一條 `.stop:3+`**:純粹調低數字會削弱「app 死掉也照樣過」那道防線
(07 以前就是門檻 2 太低而漏接過),而那三筆行程是 fixture 的資料,
app 沒真的跑起來就不存在。**門檻降了,斷言反而更強。**

### 三個(其實是五個)決定,以及理由

#### 1. 「對」存在 `localStorage`,同一個 `tokyo5-pin3`、同一筆多一個 `ok`

- **一個 key 一個答案。** 上一輪決定 1 的理由原樣適用:多一份儲存就是同一個問題有兩個答案來源,
  而那是這個 repo 反覆抓到的形狀。
- **不回存 Notion。** 那要動資料表,是另一件事的規模(跟「行程沒有『誰加的』欄位」同一個原因)。
- **代價**:只存在按下去的那台裝置上,五個人各按各的。
  但那個代價**跟它要撤掉的標記是同一個範圍** —— 虛線圈本來就只出現在按過「再查一次」的那台裝置上
  (`ap` 是重查寫進本機快取的)。**確認的作用域不會比它要撤掉的東西小**,所以沒有多欠什麼。

#### 2. `ROOFTOP`(精確)**不問**「這個位置對嗎」

- 機器有信心的時候反過來讓人背書,會把確認變成例行公事,然後**沒有人真的在看** ——
  這份 `ADOPTION.md` 裡至少有三個同形的故事(永遠在響的落後警告、被 `| tail` 接走的退出碼、
  被文件親手標成噪音的 modified 產出檔)。**一個每次都要按的確認,等於沒有確認。**
- 而且「對」的作用是讓一個**看得見的標記**退場。精確的 pin 上沒有標記可退,
  那顆按鈕按下去畫面不會有任何變化 —— 一顆沒有可觀察效果的按鈕。
- 成本那邊也一致:概略的結果是**使用者自己按出來的**(他已經在看那一筆了),
  精確的結果則到處都是,對每一顆都問一次是純粹的噪音。

#### 3. 已經確認過的再按「再查一次」

- **按鈕永遠在**,因為它就是「不對」那條路。
- 查回**同一個座標**(<50m)→ **確認留著**,flash 說「再查一次還是同一個位置」,不重問。
  確認講的是**那個座標**,不是那個名字。
- 查到**別的座標** → 那個確認**不跟著走**。新的如果又是概略,虛線圈回來、重新問。
- 查無 → 那一筆變回 `null`,pin 消失。**不留下一個兩邊都不相信的座標。**

#### 4. 快取裡那批「當初拿標題查出來的」座標:不換 key

理由寫在上面「動手前」那一節,結論是:壞的那批的判準就是「它是某一筆的標題」,
而新規則從此不讀標題那一格 —— **改讀取端比改儲存端乾淨**,也不會把大家查好的正確座標一起丟掉。

#### 5. 規則二講在 `flash()`,不講在表單裡那一欄旁邊

理由也在上面(會改到四張截圖、而 `.fld` 正在被逐塊轉換;常駐提示會變成背景)。
**表單那條方向本身是對的,登記給協調者排在 `.who` 那一塊之後。**

### `pngdiff.py` 的水平位移搜尋(協調者定為必做,做掉了)

```
--shift N   ±N 列(垂直,本來就有)
--shiftx M  ±M 行(水平,這一輪補的)
兩個一起給 → 二維搜尋,依「總位移量」由小到大,先問動得最少的那個解釋
```

拿 01 那個已登記的雙穩態當驗證(`shots/pre-input` vs `shots/pre-input-2`):

```
--band 460 640 --x 100 740 --shiftx 40
  → 最佳位移 dy=+0 dx=-27   差異像素 0/115200 (0.0000%)
  → 位移之後**逐位元組相同**:這一帶的內容沒有變,只是被推走了。
```

**比上一輪手寫那十幾行乾淨**(那次的結論是「dx=27,殘差 2.81%」,這次殘差是 0)。

**但更重要的是另一半:沒搜的方向現在會自己講出來。**
只給 `--shift` 而沒命中的時候,結論那一行從
「沒有任何位移對得上,這一帶是真的被改掉了」改成:

```
→ 在搜過的範圍裡沒有位移對得上。**但這一趟沒搜 水平(--shiftx N)** ——
   在下結論說「這一帶被改掉了」之前先把那個方向也搜一次(01 的雙穩態就是水平的)。
```

只有兩個方向都真的搜過,它才敢講那句「是真的被改掉了」。
**能力缺一半不可怕,不知道自己缺一半才可怕** —— 上一輪拿到的就是那個很有自信的錯答案。

> **用法上有一個會騙人的地方,寫進 docstring 了:`--x` 要框在捲動區的裡面。**
> 同一題用 `--x 60 780` 會回「沒有位移對得上」,因為那個範圍把**不會跟著捲的邊緣**
> 也框進來了 —— 一個真的純位移,只要框到固定不動的東西,就會看起來像是被改掉了。
