# 第三塊:`.fld label` → `rm-label`

依 `ADOPTION.md`「該改變外觀的輪」的規則:事前登記 → 改 → 比對 → 逐項對帳。

> 本檔「事前登記」以上的每一節都是**在動手之前**寫下的。
> 「實際結果」在下半部,動手之後才補。

---

## 這一輪多一欄:使用者看得出來嗎

上一輪(mono 中文後援)技術上每一步都對,但改完肉眼幾乎無感。
從這輪開始,每一項預期都要標注它屬於哪一種:

- **看得見** —— 那五個人打開網站會注意到
- **只是一致** —— 原則上對齊 design-system,但沒有人看得出來

這一輪**預期是看得見的**:標籤從 11px 淺灰細字變成 13px 深褐粗字。
做完要用截圖確認那個預期成立,不是確認「有差異」而已。

---

## 為什麼是這一塊

`ADOPTION.md`「怎麼挑一塊」的三個判準都過:

1. **語意一對一** —— 兩邊都是表單欄位標籤,沒有任何要用 utility 手拼的部分
2. **來源端最小** —— 只有一條規則,`index.html:419`
3. **不吃 `--font-mono`** —— `rm-label` 沒有設 `font-family`,走繼承(sans),
   所以它不依賴上一輪的 mono 修正,也不會被下一輪的字型工作再翻一次
4. **範圍最窄** —— 九張裡只有 **08 / 09** 兩張看得到 `.fld`,其餘七張**必須零差異**

---

## 改什麼(四處)

```
1. index.html:418  .fld{... gap:4px ...}          → gap:0
2. index.html:419  .fld label{...}                → 整條刪掉
3. index.html:433  .who label{...}                → 補回 color 與 letter-spacing(見下)
4. markup          31 個 .fld 裡的 <label>        → 加 class="rm-label"
                   + JS 產生的那一個(index.html:2853,改名欄位)
```

### 第 1 項是 Lulu 這一輪決定的

`rm-label` 自帶 `display:block; margin-bottom:.375rem`(6px),而 `.fld` 是
`display:flex; flex-direction:column; gap:4px`。**margin 會疊在 gap 上,變成 10px。**

三個選項擺給 Lulu,她選**把 `.fld` 的 gap 歸零**,讓 `rm-label` 自己的 margin 說了算 ——
間距 4px → 6px。理由:只留一套間距系統在管這件事,跟 design-system 的節奏一致,
而且「變 6px」是一個乾淨可預測的差異,好對帳。

### 第 3 項是這一輪才發現的,不在前人的規格裡

**`.fld label` 是後代選擇器,而 `.who` 住在 `.fld` 裡面。**

```html
<div class="fld"><label>誰分攤</label><div class="who" id="ef-who"></div></div>
```

`.who` 裡面每個成員是一個 `<label><input type=checkbox>名字</label>` 的膠囊。
`.who label`(:433)自己設了 `font-size:12.5px`(手機 :520 是 14px),
所以字級一直是它說了算 —— **但 `color:var(--muted)` 和 `letter-spacing:.05em`
一直是從 `.fld label` 漏下去的**,`.who label` 沒有覆寫。

把 `.fld label` 整條刪掉,那些膠囊會**跟著變色、字距變回 0**,而那不是這一輪要改的東西。

**處理:把那兩個宣告補進 `.who label`,讓膠囊逐像素不變。**
不是因為現在那樣好看,而是因為**這一輪不該碰它**。要不要讓成員膠囊也吃 design-system,
是之後某一塊的事,那時要單獨登記、單獨驗。

> 這一項**九張截圖都驗不到**(理由見下面「驗不到的地方」),所以它靠的是
> 「刪掉的宣告原樣補回同一批元素」這個推論,不是量出來的。登記在這裡。

## 事前登記:預期的視覺變化

### 每一個屬性

| 屬性 | 現在 | 之後 | 看得見? |
| --- | --- | --- | --- |
| font-size | 11px | 0.8125rem = **13px** | **看得見** |
| font-weight | 400 | **700** | **看得見** |
| color | `var(--muted)` = `#6C7385` 冷灰 | `var(--color-ink)` = **`#53443D` 暖褐** | **看得見** |
| letter-spacing | .05em(11px 時 ≈ 0.55px) | **0** | 看得見(字串變窄) |
| line-height | 繼承 body 的 1.6 → 行框 17.6px | `rm-label` 自設 **1.5** → 行框 **19.5px** | 只是一致 |
| 標籤→輸入框 | `.fld` 的 `gap:4px` | `gap:0` + margin **6px** | 看得見(微) |
| display | inline(但在 flex 容器裡本來就被 blockify) | block | **沒有效果** |

> **`--color-ink` 是 design-system 的 `#53443D`,不是 tokyo-trip 的 `--ink`(`#15171D`)。**
> tokyo-trip 的 `:root` 沒有定義任何 `--color-*`,所以這個 token 由 design-system 的
> `@layer theme` 說了算。標籤會變成**暖褐色**,不是頁面本文的近黑色。
> 這是刻意的 —— 這一塊的目的就是讓 design-system 的顏色真的長在頁面上。

### 每個欄位會長高多少

```
改前:  標籤行框 17.6px  +  gap 4px   = 21.6px
改後:  標籤行框 19.5px  +  margin 6px = 25.5px
                                        ─────
                                        +3.9px / 每個 .fld
```

## 驗不到的地方(事前講清楚)

九張截圖只看得到 **9 個**標籤(08 的 4 個 + 09 的 5 個)。
加了 class 的有 **32 個**(31 個靜態 + 1 個 JS 產生的)。**其餘 23 個沒有任何一張圖驗得到。**

| 沒被驗到的 | 在哪 | 為什麼截不到 |
| --- | --- | --- |
| `wf-*` 4 個 | 許願表單 | `#wish-form` 帶 `hidden`,05 只展開外層 `#wishbox` |
| `ef-*` 8 個 | 記一筆花費 | `#exp-form` 帶 `hidden`,沒有任何一張點過「記一筆」 |
| `xe-*` 8 個 | 改一筆花費 | `#exp-edit-overlay` 沒有任何一張打開過 |
| `si-key` 1 個 | 登入通行碼 | `#si-adminbox` 帶 `hidden` |
| `tf-time` 1 個 | 時間衝突對話框 | `#time-overlay` 要拖曳撞到才會開 |
| `rn-*`(JS) | 改名字 | 那個畫面沒有被截過 |
| `.who` 膠囊 | ef / xe 兩張表單裡 | 同上,兩個容器都沒開過 |

> **這正是 `block-02-mono` 登記過的陷阱第 1 條:DOM 裡有 ≠ 畫面上有。**
> 這 23 個在 `getComputedStyle` 上會乖乖回答新值,但它們在截圖裡永遠不出現。
> 所以本輪的驗收方式是**兩層**:
>
> 1. 截圖對帳 08 / 09 的 9 個(看得見的證據)
> 2. 在真實 DOM 上盤點全部 32 個,確認 computed 值都變成新的(涵蓋率的證據)
>
> 只做第 1 層會漏掉 23 個;只做第 2 層會重蹈「零差異也報成功」的覆轍。

### 08 / 09 的差異形狀,跟預測的機制吻合

預測寫的是「每個 `.fld` 長高 3.9px,08 把下面整片往下推、09 因為置中而整張往上移」。
實際的分群形狀正是這樣,而不是「只有標籤那幾列變了」:

- **08**:前三群很小(`y=793..828`,合計 602px)= 表單第一列的標籤本身;
  之後 `y=832..1610` 三大群共 18.4 萬 px = 表單長高之後,**底下的當日行程整片重畫**
- **09**:`y=285..405` 是對話框頂端(標題「改這一項」整個往上移),
  中段十幾個小群是逐個欄位的標籤,
  最後 `y=1388..1546`(4.6 萬 px)是對話框底部的按鈕列跟著位移

**所以 12.5% 和 10% 這兩個數字裡,絕大部分是位移不是樣式。**
這件事事前登記過(「差異面積會大得不成比例,那是位移不是樣式」),沒有變成事後歸因。

### 沒有驗到的事(講清楚)

### 順手修掉的兩個工具缺口(協調者指派)

兩個都照這裡的標準**先看過它失敗一次**再收工。

**1. `shoot.sh` 沒有併發保護。**
`.work/` 是單一共用目錄而且腳本開頭就 `rm -rf` 它,`PORT` 是單一硬編碼的 8999,
而且 build 直接把 `retro-modern.built.css` 寫進共用的工作樹。
兩隻同時跑,後跑的會 `rm -rf` 掉前一隻正在用的目錄,**兩邊都不會收到任何錯誤**。

改成開頭用 `mkdir`(原子操作)搶一把鎖,搶不到就印出持有者並 `exit 2`。
**驗證:真的同時跑兩隻**,第二隻拒絕、退出碼 2、第一隻不受影響。

> 附帶踩到一個:**腳本執行中不要改腳本自己**。
> sh 是按位元組位移邊讀邊執行的,我在第一隻還在跑的時候編輯了 `shoot.sh`,
> 位移一偏,那一隻就在半行的地方報 `syntax error near unexpected token`。
> 檔案本身沒壞,是跑到一半的那個行程被我改掉了。

**2. 出處紀錄看不到 `design-system/`。**
原本是 `git -C "$SRC" status --porcelain -- .`,`cwd` 在 `tokyo-trip/`,
`-- .` 把範圍限死在那個目錄。但 build 是從 `design-system/` 編出來的,
**而且在 `.work/` 複本拷貝之前就把產出寫進樹裡** —— 它的狀態完全決定截到什麼。

改成記整個 repo 的狀態,另外單獨列一行相依的 HEAD 和髒不髒,髒的時候多印一行 ⚠。
**驗證:故意在 `design-system/retro-modern.css` 留一個未提交的改動跑一輪**,
確認紀錄印出 `相依工作樹 1 個檔案有未提交的改動` 和那行 ⚠,然後還原。

> **原本的紀錄並不是完全瞎。** design-system 一髒,`tokyo-trip/retro-modern.built.css`
> 就會跟著變,而那個檔在 `tokyo-trip/` 底下,舊的紀錄看得到它。
> 真正的問題是:`ADOPTION.md` 自己寫過「任何人跑一次 `shoot.sh` 都會讓它變成 modified」——
> **唯一會透露凍結被打破的訊號,正好是文件教大家忽略的那一個。**

**還有一個 `set -e` 的坑,自己埋自己挖:**
我第一版把 ⚠ 寫成 `[ -n "$DIRTY_DS" ] && echo ...`,而它是 `{ } > 檔案` 區塊的最後一句。
乾淨的時候它回非零,`set -e` 會讓整支腳本在那裡**無聲結束**。改成 `if` 才對。

### 下一塊的建議

`.fld input/select/textarea` → `rm-input`。理由:同樣的兩張截圖、同樣的對照組,
而且 `.fld` 的內部間距這一輪已經理乾淨了,`rm-input` 接上去不會再有 margin 疊 gap 的問題。

**另外登記一件這一輪沒做的事**:`.who` 成員膠囊現在是「被刻意凍住的舊樣子」——
它的 `color:var(--muted)` 和 `letter-spacing:.05em` 是這一輪手動補回去的,
不是設計上的選擇。哪一天要讓它吃 design-system,那是獨立的一塊,
而且**要先讓截圖看得到它**(現在九張都看不到),不然驗不了。
