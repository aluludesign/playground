# 第二塊(其實不是一塊):`--font-mono` 的中文後援

**這一輪不是組件轉換,是修一個已經在使用者面前的回歸。**
照 `ADOPTION.md`「該改變外觀的輪」的規則做:事前登記 → 改 → 比對 → 逐項對帳。

> 本檔的「事前登記」那幾節是**在動手之前**寫下的。
> 「實際結果」在下半部,動手之後才補。

---

## 為什麼要有這一輪

`.rm-chip` 上的三顆中文分類標籤(景點／餐飲／交通)跟頁面其他中文不同一套字。
那是**第一塊造成的回歸**:轉換前 `.chip` 沒設 `font-family`,中文繼承本文;
轉換後 `.rm-chip` 用 `--font-mono`,而 mono stack 裡沒有任何 CJK 字體。

design-system 那邊已經把自己的 `--font-mono` 補好了(`7214658`),
**但那個修正到不了 tokyo-trip** —— `tokyo-trip/index.html:30` 在**無層級的 `:root`**
裡自己定義了 `--font-mono`,無層級贏過 `@layer theme`。重編後九張零差異就是證據。
辨識方法見 `block-01-chip.md`「怎麼分辨這個 computed 值是誰的 stack」。

實測(真實 DOM,不是讀 CSS 猜):

```
getComputedStyle(document.documentElement).getPropertyValue('--font-mono')
→ "IBM Plex Mono",ui-monospace,SFMono-Regular,Menlo,monospace
```

開頭是 `IBM Plex Mono`,所以說了算的是 tokyo-trip 自己那一行。

## 改什麼

`tokyo-trip/index.html:30`,一行:

```
- --font-mono:"IBM Plex Mono",ui-monospace,SFMono-Regular,Menlo,monospace;
+ --font-mono:"IBM Plex Mono",ui-monospace,SFMono-Regular,Menlo,"Noto Sans TC","PingFang TC","Microsoft JhengHei",monospace;
```

**CJK 排在所有等寬家族之後、generic `monospace` 之前。** 這個位置是刻意的:
拉丁字和數字仍然由 `IBM Plex Mono` 先接走,只有它接不住的碼位才會落到 Noto Sans TC。
形狀跟 design-system 那邊的修法一致(`7214658`),差別只在第一個等寬家族是誰。

`"Noto Sans TC"` 已經由 `index.html:10` 的 Google Fonts `<link>` 載進來了
(`--font-body` 在用),**不需要多一個網路請求**。

## 沒有走的那條路,以及為什麼

另一條是**刪掉 `:root` 的覆寫,讓 design-system 的 `--font-mono` 接手**。
Lulu 決定不走。理由:design-system 的 stack 以 `JetBrains Mono` 開頭,
那會把**站上每一個 mono 的拉丁字和數字**從 IBM Plex Mono 換成 JetBrains Mono ——
實測有 **87 個純拉丁/數字的 mono 元素**(航班板、金額、時間、DAY 標籤、票數),
血量遠大於這一輪,而且沒有人量過。

**這一輪不碰那個決定。**

### 逐字元類別:預期

改之前先查了兩邊 Google Fonts 宣告的 `unicode-range`。
**這是宣告涵蓋,不是實際渲染** —— stack 裡還有 `ui-monospace`(SF Mono)和 `Menlo`
兩個本機字體,它們沒有 `unicode-range` 限制,所以**它們有沒有那個字形會決定結果**,
而那從 CSS 看不出來。下面標 `?` 的就是這個原因。

| 類別 | IBM Plex Mono 宣告涵蓋 | Noto Sans TC 宣告涵蓋 | 預期 |
| --- | --- | --- | --- |
| 拉丁大小寫 a–z A–Z | ✅ | — | **不變** |
| 半形數字 0–9 | ✅ | — | **不變** |
| 半形標點 `!"#$%&'()*+,-./:;<=>?@[\]^_\`{\|}~` | ✅ | — | **不變** |
| `·` U+00B7、`…` U+2026、`¥` U+00A5 | ✅(在 U+0-FF / U+2000-206F) | ✅ | **不變** |
| 中文漢字 | ❌ | ✅ | **會變** |
| 平假名 / 片假名 | ❌ | ✅ | **會變** |
| 全形數字 `０-９`、全形拉丁 `Ａ` | ❌ | ✅ | **會變**,除非 SF Mono / Menlo 有 |
| 全形標點 `、。（）：～・「」` | ❌ | ✅ | **會變**,除非 SF Mono / Menlo 有 |
| `￥` U+FFE5 | ❌ | ✅ | **會變**,同上 |
| `→` U+2192 | ❌(latin 切片只到 ↑U+2191 和 ↓U+2193) | ✅ | **`?` 不確定** |
| `●` U+25CF | ❌ | ✅ | **`?` 不確定** |

**`→` 和 `●` 是這一輪最可能出現「清單外差異」的地方,所以事前登記在這裡。**
兩種結果都可能,而且都不是 bug:

- 如果 **SF Mono 或 Menlo 有那個字形** → 它們排在 Noto Sans TC 前面 → **不變**
- 如果 **兩個都沒有** → 以前落到 generic `monospace` 的系統後援,現在落到 Noto Sans TC → **會變**

會受影響的地方:`span.arr ⟨→⟩`(分帳頁 5 個)、`span.kicker ⟨TPE → NRT · Terminal 1⟩`
(行程頁)、`span.sync ⟨● 紀錄存在這台裝置⟩`。

### 一條要去推翻的斷言

> **拉丁字和數字不應該有任何變化。**

前一隻用 canvas 掃過十類字元說都沒動 —— **那個方法無效**,`ADOPTION.md` 自己寫了:
canvas 不會觸發網頁字體載入,每個 stack 都會掉到系統字體,量出來的數字看起來有意義,
其實全是同一套字。**要重量,而且要用真實 DOM 渲染。**

做法:一張獨立的探針頁,同一份 markup 渲染兩次(舊 stack / 新 stack),
每列固定高度 + `overflow:hidden`(後援字體再高也不會把下面的列推走,
所以任何一列的差異都只代表那一列自己的字形變了),然後用 `pngdiff.py` 逐像素比。
**比形狀,不比位置。**

### 預期的連帶風險(事前登記)

1. **字寬變了會回流。** Noto Sans TC 和現在的系統後援字寬不一定一樣,
   中文一變寬/變窄,同一行裡後面的拉丁數字會**跟著平移** ——
   那是**位置變了不是字形變了**,不算推翻上面那條斷言。
   對帳時要分清楚「這個像素差是字形差,還是被前面的中文推走的」。
2. **可能撐高列。** Noto Sans TC 的 line box 比系統等寬後援高的話,
   含中文的那一列會變高,底下整片跟著往下 —— 03 / 04 最可能。
3. **`.rm-chip` 是 700**,Noto Sans TC 有 700 的實體字重,
   現在的系統後援可能是合成粗體。所以三顆標籤可能**變細或變粗**,兩種都在預期內。

### 不在預期內的東西(出現就是問題)

- 顏色、邊框、圓角、背景任何改變
- 06 / 07 地圖上 pin 的**數量或座標**改變(那是 Nominatim 的事,`ADOPTION.md` 陷阱 3)
- 九張裡任何一張的正向斷言從 `✓` 變 `✗`
- `retro-modern.built.css` 的 `utilities` 層從 8 個 class 變多
  (這一輪只動 `index.html` 的一行 CSS 值,不新增任何 class 名)

### 那條要推翻的斷言:結果是「一半成立」

方法:一張獨立的探針頁,同一份 markup 用舊 / 新兩個 stack 各渲染一次,
**真實 DOM、真實網頁字體**,每列固定高度 + `overflow:hidden`(避免任何位移混進來),
再用 `pngdiff.py` 逐像素比。**沒有用 canvas。**

| 字元類別 | 差異 | |
| --- | --- | --- |
| 拉丁小寫 `a–z` | **0 px** | 逐像素相同 |
| 拉丁大寫 `A–Z` | **0 px** | 逐像素相同 |
| 半形數字 `0–9` | **0 px** | 逐像素相同 |
| 半形標點 `!"#$%&'()*+,-./:;<=>?@[\]^_` `{|}~` | **0 px** | 逐像素相同 |
| 11px/700 的拉丁數字 `Latin 0123456789 NT$1,234` | **0 px** | 逐像素相同 |
| `→ ← ↑ ↓ ● ○ • ✓` | **0 px** | 逐像素相同 |
| `TPE → NRT · Terminal 1`(站上實樣本) | **0 px** | 逐像素相同 |
| `$ ¥ € £ · …` | **0 px** | 同一列裡只有 `￥` 變 |
| **全形數字 `０１２３…`** | **2320 px** | **變了** |
| **全形拉丁 `ＡＢＣａｂｃ`** | **1482 px** | **變了** |
| 平假名 `あいうえ…` | 2842 px | 變了 |
| 片假名 `トキョウ…` | 1673 px | 變了 |
| 中文漢字 | 5521 px | 變了 |
| 全形標點 `、。（）：～・「」` | 1024 px | 變了 |
| 全形斜線等 `／｜─【】！？` | 1109 px | 變了 |
| `￥` U+FFE5 | 238 px | 變了 |
| 11px/700 中文(= chip 的條件) | 1446 px | 變了 |

**結論分兩半,不要只講前半:**

- **半形拉丁和半形數字:斷言成立。** 0 px,不是「幾乎沒動」,是逐像素相同。
  而且是在真實 DOM 上量的,不是 canvas。
- **全形數字和全形拉丁:斷言不成立,它們變了。**
  前一隻用 canvas 掃十類字元(含全形數字、日文假名)說都沒動 —— **那是假陰性**,
  因為 canvas 不觸發網頁字體載入,兩邊都掉到同一套系統字體。
  `ADOPTION.md` 已經寫了這個陷阱,但當時的結論沒有被重新量過。

站上有沒有全形數字/全形拉丁?**沒有。** 唯一用到的全形字元是
`／`(U+FF0F,出現在「託運 1 件／人」和「願望 2／3」)和中文標點。
所以**實務影響是零,但斷言本身確實被推翻了一半**,寫在這裡免得下一個人繼續引用它。

### 沒有驗到的事(講清楚)

- **航班板只在 02 / 07 兩張桌機圖被驗到。** 手機版的 `<details class="board">`
  預設關著,九張裡沒有任何一張是「手機 + 板子打開」。那個狀態沒有被截過。
- 全部是 headless Chrome + macOS 的本機字體。`PingFang TC` / `Microsoft JhengHei`
  這兩個後援**在這台機器上從來沒有被用到**(Noto Sans TC 先接走了),
  所以它們只是宣告,沒有被驗證過。
- 沒有測真實 iOS / Safari。
- 沒有測 Noto Sans TC 載入失敗(斷網、Google Fonts 擋掉)時的樣子 ——
  那時會落到 `PingFang TC`,而那條路徑沒被走過。

### 新踩到的陷阱(登記給下一個人)

1. **DOM 裡有 ≠ 畫面上有,而盤點是在 DOM 上做的。**
   `<details>` 關著的時候,裡面的元素照樣有 computed style,
   `getComputedStyle` 問什麼答什麼 —— 所以它會進你的「預期會變」清單,
   然後在截圖裡永遠不出現,看起來像「該變的沒變」。
   **盤點完要再問一句:這個元素在哪一張截圖裡真的畫得出來?**

2. **`document.fonts.check()` 回 `true` 不代表那個 family 有那個字。**
   實測:

   ```
   document.fonts.check('14px "IBM Plex Mono"', '景點')  →  true
   ```

   IBM Plex Mono 一個中文字都沒有。`check()` 問的是
   「要渲染這段文字所需要的 face 都載好了嗎」,
   沒有任何 face 宣告涵蓋那些碼位時,答案是「沒有東西要等」= `true`。
   **它是『有沒有在等網路』的檢查,不是『涵蓋不涵蓋』的檢查。**
   `ADOPTION.md` 說「一定要帶中文字當第二參數」是對的(不帶會得到假陰性),
   但帶了之後**還是可能得到誤導性的 `true`**。
   要知道涵蓋範圍,去讀 `@font-face` 的 `unicode-range`
   (`document.fonts.forEach(f => f.unicodeRange)`),不要問 `check()`。

3. **`unicode-range` 只說得出網頁字體,說不出本機字體。**
   我事前照宣告的 `unicode-range` 推論「`→` U+2192 不在 IBM Plex Mono 的切片裡,
   所以可能會變」。實測是**沒變** —— 因為 stack 裡的 `ui-monospace`(SF Mono)和
   `Menlo` 是本機字體,沒有 `unicode-range` 限制,它們先把 `→` 接走了,
   而那從 CSS 和 Google Fonts 的宣告裡完全看不出來。
   **這也正是為什麼 CJK 後援要排在 `Menlo` 之後:本機等寬字體沒有中文,
   接不住就會往下落;有的符號它們接得住,就輪不到 Noto Sans TC。**
   事前登記成「`?` 不確定,兩種結果都可能」是對的做法,不要硬猜。

4. **blur 會把差異抹到它原本不在的地方。** 09 的差異從 y=23 開始而不是 y=43,
   是 `backdrop-filter:blur(6px)` 把標題列那幾個中文字的差異往上糊了約 10px。
   看到「差異出現在一個不該有東西的位置」,先查附近有沒有濾鏡,再懷疑版面。
